## 결정과 대안 — 흐름 하나와 task 종류

흐름이 하나뿐인 실행과 task 종류별 [확정] 결정을 `references/design-summary/decisions.md`와 같은 꼴로 줄인 것이다. [확정]·[안]의 뜻도 그 파일과 같다. 여기에는 고르지 않은 대안이 적혀 있지 않다.
- **흐름이 하나뿐인 실행** [확정]: 버그 수정, 작은 요청, 설계에서 흐름이 하나로 정해진 실행은 통합 브랜치·통합 폴더를 만들지 않고 합치기·전체 검증·수정 흐름도 없다. 그 흐름의 흐름별 검증이 전체 검증의 몫(전체 관점, 실제 경로 확인)까지 맡고(크면 관점별로 나눔), 마무리·배포에서 나온 수정도 그 흐름 폴더에서 돈다. 그 흐름 브랜치가 개발 기준 브랜치에서 갈라지고 내보내기에서 그 브랜치를 넣는다. 도중에 흐름이 둘 이상으로 늘면 그때 통합 브랜치를 만들고 일반 규칙으로 돌아간다.
- **요구사항 개요** [확정: 요구사항은 두 층]: 개요는 범위 안과 밖, 묶음 지도와 묶음 사이 의존, 묶음별 요구사항 한 줄씩을 쓰고, 묶음마다(공통, 기능별) 요구사항 상세 task를 자식으로 둔다. 여러 기능이 다 있어야 확인되는 요구사항은 결과를 쓰는 쪽 묶음에 넣고 그 묶음이 의존하는 묶음을 적는다.
- **요구사항 상세** [확정: 묶음마다, 사실 전제는 전부 대조]: 묶음마다 기능·비기능 요구사항과 인수 기준(Given/When/Then)을 쓴다. 기존 코드를 전제로 한 인수 기준·가정마다 근거 위치(파일:줄)를 두고 판정자가 하나씩 열어 전부 대조하며, 대조할 자료가 없는 사실 전제는 확인 안 된 가정으로 두고 확인할 task를 지정한다. 여러 기능에 걸친 인수 기준은 결과를 쓰는 쪽 기능에 넣고(그 묶음은 의존하는 묶음 뒤에 진행) 어느 기능에도 넣을 수 없는 것만 전체 검증으로 넘긴다 [확정].
- **설계** [확정: 승인 화면 여섯 칸, 배포 계획은 여기서 사용자가 정함]: 승인 화면은 정해 주실 것 / 하실 일·허용 요청 / 알릴 결정 / 답하신 것의 반영 / 확인 안 된 가정·수용한 위험 / 관례 결정의 여섯 칸이고, 확인 질문 여섯 가운데 하나라도 "예"인 결정이 알릴 결정이다. 배포 계획(언제 배포하고 무엇을 확인할지)은 그 실행에서 가장 먼저 끝나는 설계 task가 쓰고 그 승인에서 사용자가 정한다. "배포된 것"으로 확인할 가정에서 쓰기가 있는 경로를 읽기만으로 확인하면 불합격이다 [확정].
- **구현** [확정: 사람은 예외와 동작만, 읽기 판정은 조건부, 판단할 것이 없으면 알림]: 수정 task와 코드를 고치는 변경 task도 따른다(코드를 고치는 변경은 뒤에 `kind: fix`로 바꿨다). 승인 화면에는 예외(설계에 없던 선택, 설계와 달라진 점, 판정 위치를 옮긴 인수 기준, 실제 경로로 못 돌린 검사)와 동작만 올리고 코드는 올리지 않는다. 작성자는 관련 개발 검사를 돌리고, 자체 검증은 작업 트리와 건드릴 파일의 기계 대조, 독립 실행 판정(영향 검사·기준선 밖 실패·변이 확인), 조건이 될 때만 읽기 판정(설계와 달라진 점, 인수 기준을 닫음, 가정 확인, 수정 task, 작성자 말에 의존하지 않는 기계 조건) 차례다. 통과하면 메인이 작성자의 커밋 메시지로 그 흐름 브랜치에 커밋한다 [확정: 로컬 커밋은 승인 대상이 아니다].

## 계기 사건

- 화면 설계 task가 생긴 이유(2026-10-12, 옛 화면 설계 task 정의): 화면이 요구사항 상세에서 "담당이 채움"으로(한 실행의 요구사항 정본 한 항목), 소프트웨어 설계에서 글자 목록으로(그 실행 설계 정본의 한 절) 정해져 배치·조작·상태를 설계하는 자리가 없었다. 조작 결함이 흐름별 검증에서야 나와 수정·재검증이 붙었고(그 실행의 한 검증 지적 → 수정 task 둘), 사용자가 결정하려고 "시각화해서 표현"을 되물었으며(그 실행의 한 task), 그림 품질은 구현 뒤에 사용자가 봤다(다른 실행의 한 task).
- 구현·수정 task의 알림 조건을 바꾼 일(옛 구현 task 정의): 2026-10-06 바꿈. 전에는 네 칸이 모두 비어야 알림이었다. 첫 실행에서 코드 task 15개 중 정해 주실 것이 있던 task가 0개였는데 알릴 것 한두 줄 때문에 전부 승인으로 갔고, 사용자가 승인 30번을 "많았다"고 답했다.
- 빌드·테스트 방법에 흔들림·재시도 절이 생긴 계기(옛 build-and-test 「흔들림과 재시도」): 재시도가 30곳에 켜진 worker 시험의 표준 명령 출력에 흔적이 없어 작성자는 JSON만 보고 "재시도 0"이라 보고했고, 판정자가 verbose로 돌리니 3건이었다(2026-10-06). 그 뒤의 판정도 근거 없이 "흔들림 0"으로 나갔다(2026-10-07 시험 리뷰).
- 시험 작성 기준의 사례 출처(옛 test-rules 머리): 규칙마다 붙었던 괄호 안 사례는 시험 리뷰를 한 실행(2026-10-07)에서 나왔다. 규칙의 근거는 사례가 아니라 시험 작성 기준 첫머리의 원리다.
- 시험 작성 기준 ①의 사례: 같은 흐름을 12구성으로 반복한 E2E, 단위와 겹친 거절 5건·펼침 4건·9구성.
- 시험 작성 기준 ②의 사례: 권한이 열려도 406·503이면 통과하는 거부 단언, 연결이 끊겨도 통과하는 제약 단언, undefined도 통과하는 `not.toBe('')`, 문구가 바뀌면 빈 단언이 되는 사본, 경로 둘을 다 받는 단언, 빈 그림도 통과하는 단언.
- 시험 작성 기준 ③의 사례: 2초 창 8회, 만료 6초 고정 대기, 5초 제한을 실시간으로 기다림.
- 시험 작성 기준 ④의 사례: worker `retry: 1` 30곳이 값 실패도 한 번 흡수했다. `--reporter=verbose`를 붙이면 `(retry x1)`이 보였지만 표준 명령은 vitest 4의 `agent` 리포터라 아무것도 남지 않았고, 판정은 늘 "흔들림 0"이었다.
- 시험 작성 기준 ⑤의 사례: dev 방문과 겹치면 거짓 실패하고 정리 훅이 없어 실행마다 행이 남음, 중단되면 바뀐 사진이 남아 다음 회차가 원인 없는 실패.
- 시험 작성 기준 ⑥의 사례: 사진 없는 폴더에서 60초 시간 초과가 쌓임, 마이그레이션이 없으면 skip 4건으로 녹색, build 없이 돌리면 거짓 실패 4건.
- 시험 작성 기준 ⑦의 사례: 늘 "다름 5건"이라 정답 파일 변조를 못 잡음.

실행 기록의 사건 E-01~E-32는 `references/design-summary/events-runs.md`에 있다.

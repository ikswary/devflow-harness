## 결정과 대안

- 기획 task 자리의 이유(옛 기획 task 정의): 처음엔 요구사항 앞(왜·누가·단계)에, 다음엔 모든 상세 뒤에 두었다가 사용자가 "개요 뒤, 상세 앞"으로 정했다(2026-10-12). 범위가 정해진 뒤이고, task 하나가 상세들의 부채꼴 앞에 와서 병목이 작으며(모든 상세 뒤에 두면 한 실행에서 공통 설계가 약 5시간 늦어졌다), 정책을 기획이 먼저 정하고 상세가 FR로 옮기므로 정책 표가 FR과 중복되지 않는다.

하네스 설계의 결정과 고르지 않은 대안을 줄인 것이다. [확정]은 사용자가 선택지를 보고 고른 것, [안]은 항목별 확인 없이 출발점으로 둔 것이다.
- **한 살이** [확정]: 모든 task가 같은 상태를 가진다. 종류별 한 살이를 두지 않는다. 옛 상태 `멈춤`은 뒤에 뺐다.
- **파이프라인 없음** [확정]: 요청에 맞는 시작 task만 고르고, 기다리는 것은 머리 파일에 적힌 의존뿐이다. 요구사항 블록은 사용자에게 보이는 동작을 바꾸는 요청에만 쓴다.
- **승인 답** [확정]: 선택지는 승인 / 고칠 것이 있음 / 나눠서 다시 / 보류로 고정한다. 산출물을 바꾸는 답이면 원래 task를 닫고 변경 task를 만든다. 고르지 않은 대안: 이전 판처럼 고친 뒤 같은 화면이 다시 오게 하는 것(바뀐 부분만 변경 task의 승인으로 온다).
- **변경 task 줄이기** [확정]: 작성자는 결정 지도를 먼저 쓰고 답 없는 사용자 결정이 있으면 본문을 쓰지 않고 닫는다. 답에 따라 문장 몇 개만 달라지면 선택지별 문장을 미리 써서 고르면 끝나게 한다.
- **사람에게 두 번 가는 일** [안, 리뷰 채택]: 예외 상태를 두지 않고 task 둘로 나눈다(질문 → 본 task, 검증 → 재검증, 배포 계획 → 배포 실행). 합치기와 내보내기는 계획이 스크립트 출력이나 명령 한두 줄이라 나눌 실익이 약해 task 하나의 앞 절반·뒤 절반으로 시작하고, 첫 실행 뒤 사용성을 보고 다시 정한다 [확정].
- **고칠 것은 늘 새 task** [확정]: 정본을 고치는 변경 task는 고친 판을 자기 task 폴더에 쓰고 메인이 스크립트로 옮긴다.
- **스스로 줄이는 통로** [확정: 크기를 숫자로 강제하지 않음]: 답 없는 결정, 항목이 많다는 작성자 판단, 컨텍스트 문턱. 둘째는 막지 않고 칸별 항목 수를 화면에 적어 강제할 값의 근거를 쌓는다. 셋째는 첫 실행 뒤로 미뤘다.
- **나누기** [확정]: 나누는 축과 숫자를 규칙으로 정하지 않는다. 출발점은 기능 묶음이고 둘 이상이 의존하는 것은 공통으로 먼저 끝낸다. 숫자는 나눔을 검토하라는 신호로만 쓴다.
- **판정자** [확정]: 그 task의 작성·수정 지시·수정에 참여하지 않은 에이전트가 판정하고, 메인은 기계적 대조만 한다. 근거: 이전 판의 독립 판정이 놓친 원인은 판정자가 누구냐가 아니라 무엇을 봤느냐였다. 그래서 원 산출물을 직접 보고 기록만 본 기준은 통과로 세지 않는다.
- **검사 책임과 재사용** [확정]: 작성자는 관련 개발 검사로 피드백을 받고, 독립 판정자가 영향 기반 최종 검사를 실행한다. 재판정은 실패와 수정 영향만 보되 영향 불명은 넓힌다. 독립 결과 재사용은 제품·시험·설정·의존성·명령·환경 초기화 입력과 독립 근거가 모두 같을 때만 한다. URL이나 tree 동일만으로 DB 상태를 같다고 보지 않는다.
- **공유 자원 대기** [확정]: 사용 중인 공유 자원은 실패·판정불가·환경 재시도 소진으로 다루지 않는다. 메인이 순서를 정하고 task를 자체검증에 둔 채 안 한 검사만 잇는다. 기다리며 잠금을 쥐지 않는다.
- **통과 못 한 task** [확정]: 승인 화면 맨 위에 올리고 변경 / 원인 분석 / 위험을 받아들임(백로그) / 보류 가운데 고르게 한다.
- **승인 화면과 대기열** [확정]: 칸의 틀을 고정하고, 한 번에 task 하나만 묻고 묶어서 승인받지 않는다. 판단할 것이 없는 결과는 알림으로 지나간다(구현·수정의 알림 조건은 2026-10-06에 바꿨다, 계기 사건).
- **폴더와 브랜치** [확정]: 흐름마다 폴더(worktree)와 브랜치, 통합 폴더는 따로 둔다. 원래 폴더는 실행 내내 건드리지 않고 예외는 내보내기의 병합이다. 폴더 규칙은 실행마다 묻지 않고, 프로젝트마다 다른 것(의존성 설치, 비밀 파일)만 첫 실행 때 정한다.
- **밖으로 나가는 것** [확정]: 합치기·개발 기준 브랜치에 넣기·push·PR·배포는 실행될 내용을 그대로 보여 주고 승인받는다. 승인 한 번은 그 실행 한 번에만 유효하고, 저장소 밖에 닿는 명령은 에이전트가 아니라 메인이 실행한다.
- **상태 기록** [확정]: task마다 파일, 보드는 생성물, 경과는 덧붙이기 전용 파일. 고르지 않은 대안: 이전 판의 상태 파일 하나.
- **조율** [확정]: 메인 세션 하나가 에이전트를 띄우고 상태를 바꾸며 승인을 받는다. 에이전트는 task 하나만 맡고 끝나며, 실행 중인 에이전트에 정정 메시지를 보내지 않는다.
- **이전 판에서 버린 것**: 블록 절차(계획 → 승인 → 실행 → 게이트 → 승인), 파이프라인, 상태 파일 하나, 블록이 끝날 때까지 사는 담당과 교체 인계, 검증 블록 안의 수정 루프, 커밋 분할안과 남은 일 절, 계획 파일의 승인 반영 절.
- **다시 열기**(11, 2026-10-06 사용자 결정): 끝난 실행은 후속 요청(그 실행의 정본과 결정을 그대로 이어 쓰는 요청)일 때만 다시 열어 이어 붙인다. 고르지 않은 대안: 다시 열지 않음(앞 규칙), 백로그 전부를 후속으로 받음(한 실행이 끝없이 길어지고 지표 구간이 흐려진다).
- **시작 task** [확정]: 새 기능·기능 변경은 요구사항 개요, 버그는 원인 분석, 동작을 바꾸지 않는 변경은 설계, 이미 있는 변경의 리뷰는 검증, 배포만은 배포 계획, 백로그 처리는 그 task의 종류로 시작한다(앞은 필요하면 질문 task). 리뷰로 시작은 그런 요청이 올 때 넣는다.
- **검증** [확정: 검증은 두 층]: 흐름별 검증은 알림으로 지나간 구현 task를 표본이 아니라 전부 다시 읽고 숨은 예외를 task별로 기록한다(드물다는 것이 기록으로 확인되면 표본으로 내림). 재검증은 새 지적이 없으면 알림으로 끝난다.
- **합치기** [확정: 끝나는 대로, 합칠 때마다 승인]: 충돌이 없고 영향 검사가 통과하면 알림으로 끝난다. 합쳐진 코드의 수정은 수정 흐름에서 차례로 돌고 모아서 한 번 합친다. 마지막 합치기는 최종 배포 후보의 전체 검증을 매번 새로 실행해 commit과 artifact를 묶는다.
- **배포** [확정: 시점은 실행마다 정함, 반복 배포도 매번 승인]: 언제 몇 번 배포할지는 설계의 배포 계획에서 사용자가 정한다. 환경이 둘 이상이면 계획은 함께 쓰고 실행은 차례로 하며, 운영은 dev에서 유지·확인 통과한 커밋을 그대로 올린다(고르지 않은 대안: dev 끝과 대조해 문서만 다르면 맞춰 올림 — 문서가 배포 동작을 바꾸는 프로젝트와 커밋 해시 빌드 식별자에서 깨졌다). 확인이 실패해도 되돌리기를 지시하지 않고 묻는다. 첫 환경을 만드는 배포 준비 task는 아직 없다(넣지 않은 것).
- **실행하면서 정하는 값**: 나누는 기준·승인의 크기·동시 흐름 수·상한·재시도·모델·배포 시점은 `run.md` 「이번 실행의 값」에 적고, 지난 값과 결과를 보여 준 뒤 사용자가 고른다.

흐름이 하나뿐인 실행과 task 종류별 결정은 `references/design-summary/decisions-tasks.md`에 있다.

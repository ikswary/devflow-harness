# 코드 판단 기록

읽는 kind: `implementation`, `fe-implementation`, `be-implementation`, `fix`. 1.2.0부터 시작한 task에 적용한다.

코드에는 설계가 정하지 않아 구현이 정한 것이 남는다. 문장으로는 문제가 드러나지 않는 판단은 사람이 코드로 보므로, 어떤 판단이 어디에 있는지를 기록한다. 칸을 정하는 순서(`references/roles/writer.md` 2절)는 그대로이고, 사용자가 정할 결정은 이 기록과 별개로 「정해 주실 것」에 쓴다.

## 작성자: 결과 파일 「판단」 절

판단마다 한 줄을 쓴다. 판단이 없으면 `- 없음`이다.

`- {무엇을 어떻게 정했는지} [종류: 구조] [위치: 파일:줄]`

- 종류는 이 여덟뿐이다. 이름 짓기와 형식은 세지 않는다.

| 종류 | 무엇을 정했나 |
|---|---|
| `구조` | 모듈과 파일의 나눔, 공개 범위, 의존 방향, 재사용과 새로 만듦 |
| `데이터` | 저장 형식, 스키마, 값의 변환과 정합 |
| `트랜잭션` | 묶는 범위, 순서, 동시성, 재시도와 멱등 |
| `오류` | 무엇을 잡고 무엇을 올리는가, 실패 때 상태 |
| `외부호출` | 외부 서비스와 프로세스, 제한 시간, 실패 처리 |
| `보안` | 인증, 권한, 비밀값, 입력 검증, 개인정보 |
| `동작` | 사용자나 호출자가 겪는 경계 사례와 기본값 |
| `시험` | 시험 범위, 대역, 기대값을 정한 방식 |

- 기존 코드의 꼴을 따른 구조 판단은 `[따름: 파일:줄]`을 더한다.
- 설계나 사용자 답이 정한 것은 판단이 아니다. `- {무엇} [설계: {절 또는 답 시각}]`으로 적는다. 종류와 위치는 쓰지 않는다.
- `[위치]`는 그 판단이 드러나는 코드 한 곳이다. 여러 곳이면 줄을 나눈다.

## 읽기 판정자: 판정 파일 「판단 대조」 절

칸 분류 확인 뒤에 쓴다. 적을 것이 없으면 `- 없음`이다. 이 절의 줄은 판정 결과를 바꾸지 않는다.

- **`[설계:]` 대조**: 값이 절이면 task 폴더 `design-copy\`의 사본, 답 시각이면 `decisions.md`와 머리 파일 「승인 기록」, 시작 뒤 승인된 변경이면 그 task의 결과를 본다. `design-copy\hashes.md`가 없으면 사본을 뜨지 못한 것이므로 지금 정본으로 대조하고 그 사실을 적는다.
  - 근거에 있는데 코드가 다르면 달라진 점을 빠뜨린 것이고 기준의 실패다.
  - 어디에도 없으면 그 줄은 작성자의 판단이다. 실패로 세지 않고 숨은 판단으로 적는다.
- `숨은 판단: {위치} | {내용} | {종류}`: "규약과 설계를 지켰는가"와 따로 "작성자가 적지 않은 판단이 있는가"를 묻고 적는다.
- `종류 이의: {그 줄의 앞부분} | {작성자 종류} → {판정자 종류}`: 종류가 코드를 보는 길을 가르므로 작성자 표시를 믿지 않는다.
- `같은 곳: {위치} | {위치}`: 파일은 달라도 한 판단으로 함께 봐야 하는 위치를 잇는다.
- `사람이 볼 곳: {위치} | {깨지는 조건 한 문장}`: 판단이 없어도 틀리면 위험한 곳을 지목한다. 기본은 `사람이 볼 곳: 지목 없음`이고 이 줄은 늘 쓴다. 채우려고 찾지 않고, 지목해도 3곳까지다(금액의 유일한 계산 지점이 바뀜 같은 곳).
- `같은 판단: {그 줄의 앞부분} | {앞 task}`: 앞 task에서 이미 나온 판단이 다시 나왔을 때 잇는다. 같은 실행의 코드 task `result.md`를 `grep`해 찾는다.
- `코드 의견: {위치} | 일어난 일 | 지금 문제 있음/없음 | 깨지는 조건 | 저장소에서 같은 문제를 푸는 방식`: `구조`, `데이터`, `트랜잭션`, `오류`, `외부호출`, `보안` 종류의 판단과 숨은 판단마다, 프롬프트가 준 보안 신호 위치마다 한 줄이다. 일어난 일은 코드가 실제로 하는 일을 쓴다. 고르라고 권하지 않는다. 사람이 볼지는 뒤에 정해지므로 판정 때 가리지 않는다.

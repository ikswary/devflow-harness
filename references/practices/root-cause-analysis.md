# 원인 분석 절차

읽는 kind: `question`, `root-cause`.

증상을 가리는 수정과 원인을 고치는 수정은 겉보기에 같다. 차이는 증거다. 이 절차는 "왜 그런지"를 증거로 남겨 구현·검증 task가 그 증거를 기준으로 판단하게 한다.

## 1. 증상 정리
- 기대 동작 / 실제 동작 / 발생 조건(입력, 환경, 빈도) / 최초 발생 시점(알면 해당 시기 커밋).
- 스택 트레이스가 있으면 가장 안쪽의 **프로젝트 코드** 프레임부터 본다.

## 2. 재현
- 우선순위: 단위 테스트 > 통합 테스트(`@SpringBootTest`, testcontainers 등) > 스크립트·HTTP 요청 > 수동 절차.
- 재현 테스트 이름은 증상을 설명한다: `대여_연장_시_반납일이_두번_더해지지_않는다`.
- 재현이 안 되면 조건을 바꿔 가며 시도한 목록을 남긴다. 재현 실패도 정보다.

## 3. 가설 확인
| # | 가설 | 확인 방법 | 결과 | 근거 |
|---|---|---|---|---|
| H1 | ... | 로그 추가 / 값 출력 / 코드 경로 추적 / git blame | 확인·기각 | 파일:줄, 출력 |

- 가장 싼 확인부터 한다.
- `git log -L 시작,끝:파일` / `git blame -L 시작,끝 파일`로 해당 줄이 언제 왜 바뀌었는지 본다. 범위 없이 돌리면 큰 파일에서 출력이 수천 줄이 되어 컨텍스트를 채운다. 최근 변경이 원인인 경우가 많다.
- 조사용 로그 코드는 끝나면 모두 되돌린다.

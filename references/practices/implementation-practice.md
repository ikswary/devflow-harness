# 구현 방법

읽는 kind: `implementation`, `fix`.

## 작업 하나 구현하기
1. 설계서가 지정한 본보기 코드를 읽는다. 이름, 패키지 위치, 예외 처리, 로깅, 트랜잭션 표기를 그대로 따른다.
2. 가능하면 테스트를 먼저 쓴다(특히 버그 수정의 재현 테스트). 테스트를 쓰거나 고칠 때는 같은 폴더의 `test-rules.md`(시험 작성 기준 ①~⑦)를 따른다. 판정자가 이 번호로 판정한다.
3. 구현한다. 설계와 다르게 해야 하면 이유를 메모한다.
4. 해당 모듈만 빌드·테스트한다(`build-and-test`의 모듈 단위 명령). 실패를 다음 작업으로 미루지 않는다.

## 하지 않는 것
- 설계 범위 밖 리팩터링, 포매팅만 바꾸는 대량 변경(리뷰 diff가 오염된다).

## 수정 요청 처리
- 판정 실패: 실패 로그의 첫 원인부터 고친다. 연쇄 실패일 수 있다.
- 리뷰 지적: 지적 ID별로 `수정함 / 수정 안 함(이유)`을 결과 파일에 남긴다. 동의하지 않는 지적은 고치지 말고 이유를 적는다 — 판단은 사용자가 한다.

# 설계서 작성법

읽는 kind: `question`, `design`, `change`.

설계서는 구현자가 추가 질문 없이 작업을 시작할 수 있을 만큼 구체적이어야 하고, 리뷰어가 "왜 이렇게 했는지"를 판단할 수 있을 만큼 이유가 있어야 한다.

## 조사 순서
1. `recon.md`의 아키텍처 요약과 코드 관례를 읽는다.
2. 변경과 가장 비슷한 기존 기능을 찾아 그 흐름(컨트롤러부터 저장소까지)을 따라 읽는다. 새 코드는 이 기능을 본보기로 삼는다.
3. 변경이 닿는 공용 코드(예외 처리기, 공통 응답, 보안 설정, 트랜잭션 설정)를 확인한다.

## 난이도 기준

| 난이도 | 기준 | 구현 모델 |
|---|---|---|
| 단순 | 기존 패턴을 그대로 따라 쓰는 작업. 판단할 것이 없음(DTO, 매퍼, 설정값, 반복 CRUD, 단순 테스트 픽스처) | sonnet |
| 일반 | 기존 패턴을 따르지만 로직·예외 처리 판단이 필요 | opus |
| 복잡 | 새 구조, 동시성, 트랜잭션 경계, 성능, 보안이 걸림 | opus |

작업 하나는 한 번에 리뷰할 수 있는 크기(대략 파일 1~4개)로 자른다. 같은 파일을 여러 작업이 건드리면 선행 관계로 묶는다(병렬 구현 시 충돌 방지).

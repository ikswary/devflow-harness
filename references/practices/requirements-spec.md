# 요구사항 명세 작성법

읽는 kind: `req-overview`, `req-detail`.

명세의 목적은 "끝났는지 판정할 수 있게" 만드는 것이다. 인수 기준은 검증 task에서 그대로 추적표가 되므로, 판정 불가능한 문장은 뒤에서 반드시 문제가 된다.

## 질문 만들기

- 코드를 읽어 알 수 있는 것은 묻지 않는다.
- 답에 따라 범위나 동작이 달라지는 것만 묻는다. 최대 7개, 중요한 순서로.
- 각 질문에 **추천 답과 이유**를 붙인다. 사용자는 대부분 추천을 고르므로 좋은 추천이 승인 속도를 올린다.
- 형식: `Q1. {질문} — 추천: {답} (이유: {한 줄}) / 대안: {답}`
- 앞 실행의 지적·항목 번호(V-01 등)는 내용 한 줄과 함께 쓴다. 메인이 이 질문을 그대로 사용자에게 옮기며, 사용자는 번호를 기억하지 않는다.

## 좋은 인수 기준의 조건

- Then은 관찰 가능한 결과다: HTTP 상태·응답 필드, DB 상태, 로그, 화면 요소.
- "적절히", "빠르게", "잘", "등"이 없다. 성능은 숫자로 쓴다.
- 오류 경로도 쓴다: 잘못된 입력, 권한 없음, 없는 리소스, 동시 요청.
- 기존 동작이 바뀌면 "기존 X는 유지된다"도 인수 기준으로 넣는다(회귀 방지).

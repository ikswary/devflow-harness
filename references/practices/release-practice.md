# 마무리와 배포

읽는 kind: `wrap-up`, `deploy-plan`, `deploy-exec`.

## A. 마무리

### 커밋
- 스타일: `git log --oneline -20`에서 형식을 따른다(예: `type: [scope] 설명`, 한글/영문 여부).

### PR 설명
```markdown
## 배경
## 변경 내용
## 테스트
- 자동: {실행한 테스트와 결과}
- 수동: {확인 방법}
## 리뷰 포인트
## 배포 시 주의
```
PR 생성은 `gh pr create`를 쓰며, 사용자가 마무리 task의 실행 승인에서 PR 방식을 고른 경우에만 한다.

### 배포 메모
DB 마이그레이션(순서, 되돌리기 가능 여부), 새 환경 변수·시크릿 이름, 기능 플래그, 의존 서비스 순서, 롤백 시 주의, 검증 결과의 「배포 전에 시험하지 못한 경로」(배포 계획 task가 배포 후 확인 항목으로 쓴다).

### 남은 일
검증 task의 미해결 지적(ID·심각도), 요구사항의 범위 밖·가정, 구현 결과의 제안 항목을 한 표로 모은다.

## B. 배포

### 배포 방식 탐지 (근거 파일 필수)
| 단서 | 의미 |
|---|---|
| `.github/workflows/*.yml`의 `on: push`/`workflow_dispatch` + deploy 잡 | CI 배포 — 직접 배포 대신 push·태그·`gh workflow run`으로 트리거 |
| `Dockerfile` + `docker-compose*.yml` | 컨테이너 빌드·실행 |
| k8s 매니페스트, `Chart.yaml`, `kustomization.yaml` | `kubectl`/`helm` 배포 |
| `serverless.yml`, `template.yaml`(SAM), `cdk.json` | 서버리스 배포 |
| `deploy*.sh`, Makefile `deploy` 타깃 | 프로젝트 전용 스크립트 — 내용을 읽고 무엇을 하는지 요약 |

CI 배포가 있으면 로컬에서 직접 배포하지 말고 CI를 트리거하는 방식을 우선 제안한다. 운영 경로를 우회하면 감사 기록과 환경 설정이 어긋난다.

### 명령 계획
- 자리 표시 없이 그대로 실행할 형태로 번호를 매겨 쓴다.
- 각 명령 옆에 예상 결과와 실패 시 멈출지 여부를 적는다.
- 롤백도 같은 형식으로 쓴다(이전 이미지 태그, 이전 릴리스, `git revert` 후 재배포 등).

### 배포 후 확인
헬스 체크 엔드포인트(Spring Actuator `/actuator/health` 등), 핵심 API 스모크 요청, 배포 직후 에러 로그. 확인 방법이 없으면 사용자에게 무엇을 보면 되는지 질문으로 남긴다.

읽기 위주 확인은 연결·권한·중계 서비스 문제를 놓친다. 그래서 dev 같은 비운영 환경에서는 핵심 쓰기 흐름 1건을 배포된 경로로 실제 실행한다(배포 메모의 「배포 전에 시험하지 못한 경로」가 있으면 그 경로부터). 명령 목록에 그대로 넣어 승인받고, 확인용 표시·정리 방법·실행 시점(첫 배포와 연결 설정을 바꾼 배포)·dev DB 잠금 같은 공유 자원 규칙과의 관계를 적는다. 운영에서는 쓰지 않는다. 운영의 쓰기 경로는 dev가 운영과 같은 경로(연결 방식·중계 서비스·설정 종류)를 쓰는 것으로 보증한다. 그래서 계획에 dev와 운영의 경로를 나란히 적고, 다르면 배포 전에 맞춘다(값만 다르고 종류가 같으면 허용). 운영 배포의 확인은 읽기와, 배포 직후 첫 실제 요청의 로그 보기까지다.

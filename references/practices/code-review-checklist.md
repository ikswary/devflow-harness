# 코드 리뷰 기준

읽는 kind: `flow-verify`, `reverify`, `full-verify`.

리뷰의 가치는 지적 개수가 아니라 **실제로 틀리는 경우를 찾는 것**이다. 시나리오 없는 지적은 사용자의 승인 시간을 낭비한다.

## 관점

| 관점 | 보는 것 |
|---|---|
| 정확성 | 요구사항·인수 기준 충족, 경계값, null/빈 값, 예외 경로, 상태 전이, 동시성, 트랜잭션 경계, 기존 동작 회귀 |
| 보안 | 인증·인가 누락, 입력 검증, 인젝션(SQL/명령/경로), 민감정보 로그·응답 노출, 시크릿 하드코딩, 권한 상승 |
| 성능 | N+1 쿼리, 반복 안의 I/O, 페이지네이션 없는 전체 조회, 인덱스 없는 조건, 큰 객체 메모리 적재, 불필요한 동기 호출 |
| 유지보수성 | 기존 관례와의 불일치, 중복, 책임 혼재, 이름, 숨은 결합, 설명 없는 매직 값 |
| 테스트 충분성 | 인수 기준별 테스트 존재, 오류 경로 테스트, 과도한 모킹으로 아무것도 검증하지 않는 테스트, 불안정한 테스트(시간·순서 의존). 이번 변경이 더하거나 고친 시험은 `references/practices/test-rules.md` ①~⑦로 보고, 지적에 규칙 번호를 붙인다(주석에 결정 번호가 있는 예외와 기존 시험은 지적하지 않음) |

스택별 체크 포인트는 해당 스택 문서만 읽는다:
- Spring·Kotlin/Java → `references/practices/stacks/spring-jvm.md`
- Python → `references/practices/stacks/python.md`
- Node/TypeScript → `references/practices/stacks/node-ts.md`

## 심각도

| 심각도 | 기준 |
|---|---|
| 차단 | 인수 기준 불충족, 데이터 손상·유실, 보안 취약점, 기존 기능 회귀, 빌드·테스트 실패 |
| 중요 | 특정 조건에서 틀리는 동작, 운영 문제(성능·장애 대응) 가능성이 구체적 |
| 권장 | 유지보수성·가독성 개선, 테스트 보강 |

틀리는 입력·상황을 구체적으로 쓸 수 없으면 `권장`보다 높이지 않는다.

## 지적 형식

```markdown
### [R-{관점 약어}{번호}] {한 줄 요약} — {심각도}
- 위치: {파일}:{줄}
- 문제: {무엇이 왜 틀리는가}
- 시나리오: {어떤 입력·상황 → 어떤 잘못된 결과}
- 제안: {고치는 방향}
- 확인 상태: 확인됨 / 근거 부족
```
관점 약어: COR(정확성), SEC(보안), PERF(성능), MNT(유지보수성), TST(테스트).

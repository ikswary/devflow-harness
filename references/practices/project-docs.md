# 프로젝트 산출물

메인이 읽는다(실행의 시작과 끝, 마무리). 읽는 kind: 없음. 작성자는 `writer.md` 줄이 가리키면 2절, 마무리 작성자는 4절의 문서를 읽는다. `docs_base_commit`이 있는 실행에 쓰고, 옛 실행은 지금까지처럼 실행 폴더에만 정본을 둔다.

사람에게 보일 때 변경판은 "이번 실행의 문서", 넣기는 "프로젝트에 넣기"다.

## 1. 대응표

| 실행 폴더 | 프로젝트 |
|---|---|
| `spec\brief.md` | `docs/product/brief.md` |
| `spec\overview.md`, `spec\{묶음}.md` | `docs/product/requirements/` 같은 이름 |
| `spec\overview.md` 「용어」 | `docs/product/glossary.md` |
| `ui\{화면}.md`, `ui\wireframes\` | `docs/screens/` 같은 이름 |
| `design\{흐름}.md`의 기능 흐름도와 결정 절 | `docs/architecture/flows/{흐름}.md` |
| `design\infra.md` | `docs/architecture/infra.md` |

표는 `scripts/project_docs.py`에 있다. 설계 정본의 자식 행처럼 그 실행에만 참인 줄과 「변경 이력」은 넣지 않고 실행 폴더에 남는다. 그 밖의 위치: `docs/generated/`(구조도, 데이터 모델, API, 테스트 지도. 직접 고치지 않음), `docs/decisions/`(번호 고정. 뒤집히면 새 기록이 대체), `docs/operations/`(운영·되돌리기, `unverified.md`, 위협 모델). 캡처는 git에 넣지 않고 다시 뽑는다.

## 2. 변경판과 현재 상태 꼴

- 기준본은 `base\docs\…`이고 시작 커밋에서 뜬 사본이다. 고치지 않는다. 다른 묶음의 문서를 볼 때 읽는다.
- 실행 폴더에는 **이번 실행이 고치는 파일만** 둔다. 다른 파일을 복사해 두지 않는다. `spec\` 안의 파일은 이번 실행의 것으로 읽힌다.
- 고치는 파일이 기준본에 있으면 **그 파일을 통째로 복사해 고친다**(파일 단위 전체 사본). 문서는 언제나 지금 상태를 쓴다: `## 회차 {n}` 절, "이번에 바뀌는 것만", 앞 판을 가리키는 설명을 넣지 않는다. 차이는 스크립트가 기준본과 견주어 보인다.
- 기준본에 없는 문서는 건드리는 영역만 채운다(기존 프로젝트의 첫 실행). 이때 그대로인 곳은 "기존 그대로(파일:줄)"로 둔다.
- 기준본의 첫 판을 쓰는 task는 「고치는」 task가 아니다. 고치는 task는 이 실행에서 이미 승인한 판을 고치는 등록표 `change`다.

## 3. 승인 해시

스크립트가 찍는다. 줄 끝은 정규화한다. 찍은 판의 사본은 `approved\`에 남는다. 메인과 작성자는 해시 파일을 손으로 고치지 않는다.

- 승인을 물을 때(`→승인대기`): 쓴 정본과 고친 판, 결과, 판정, 마무리 리뷰의 사본을 `approved\asked\{id}\`에 뜬다. 사람이 본 판과 설명의 근거다. 화면 뒤에 쓴 글은 근거가 아니다.
- 완료 전이: 지금 글과 물을 때의 판의 차이가 답이 고른 선택지(`선택지 (가)의 문장:`, `(가) …`의 본문이 줄과 같음, `지금:`→`바뀜:`)로 설명되면 지금 글을 찍는다. 답은 물은 뒤의 답 줄 전부에서 읽고, 문장을 감싼 따옴표와 백틱, 끝의 위치 괄호는 벗겨 견준다. 판정 파일에서는 답이 고른 `대안 문장:`만 근거다. 설명되지 않거나 답이 어느 선택지인지 읽히지 않으면 물을 때의 판을 찍어 `승인 화면 뒤 달라짐`으로 보인다. 사본이 없으면 `대조하지 못함`이다.
- 「앞 정본 줄」의 파일: 답이 고른 선택지의 줄이고, 마지막 승인 판과의 차이가 그 줄로 설명될 때만 다시 찍는다. 그 밖에는 찍지 않아 달라진 줄이 그대로 보인다.
- `apply_revision.py`: 고친 판을 옮기고 이력 줄을 붙인 뒤에 찍는다. 대조는 완료 전이와 같고 HTML은 그대로 견준다.

## 4. 넣기

`project-docs/insert.md`: 표의 말, 같은 절 두 곳의 답, 다시 넣기, 마무리 작성자가 쓰는 것, 테스트 지도.

## 5. 생성 명령

프로젝트 설정의 `## 생성 명령` 절에 `- {이름} | {명령} | {docs/generated/파일}`로 둔다. 명령에는 `|`가 들어가도 된다. 표준 출력이 그 파일이 된다. 넣는 것은 생성본이다. 마무리에서 한 번 뽑고(`--generate {코드 폴더}`) 실행 판정이 `--generate {코드 폴더} --check`로 대조한다. 다르면 실패다. 테스트 지도는 이 대조에서 뺀다.

**작성자가 만든 명령은 사람이 승인하기 전에 돌리지 않는다.** 작성자는 돌려 보지 않고 제안 줄만 쓴다. 줄은 실행 승인 화면 「넣을 산출물」에 전문으로 오르고, 승인 답을 적을 때 `task_set.py`가 물을 때의 화면에 실린 줄만 설정에 등록한다. 위임 답으로는 등록하지 않는다. 그 명령을 빼라는 답이면 작성자가 줄을 지운 뒤 다시 묻는다. 등록한 명령은 다음 넣기와 다음 흐름 리뷰부터 돈다.

등록한 명령의 안전장치: 시간 제한(프로세스 나무째 종료), 전후 `git status` 대조(`생성 명령이 코드 폴더를 고침: {파일}`), 코드 끝(sha)별 한 번만 실행. 실패와 시간 초과는 승인을 막지 않고 사유만 싣는다. 못 읽은 줄은 경고한다.

설계의 제안 도면은 이름이 같은 생성 명령의 출력과 줄로 견주어, 다른 줄만 흐름 리뷰 한 장의 「설계와 달라진 점」에 오른다. 달라도 실패가 아니다. 도면은 코드 원문으로 보인다.

기존 프로젝트의 첫 기능 실행은 생성 산출물과 시스템 구성도를 만들고, 나머지는 건드리는 영역만 채운다.

## 6. 낡음

상태는 `_workspace\policies\docs-state.md`다. 문서 안에 두면 넣은 뒤 다시 커밋해야 한다. 생성물은 다시 뽑고 결정 기록은 고치지 않으므로 작성 문서만 다룬다.

| 때 | 하는 것 |
|---|---|
| git 훅 | 프로젝트마다 처음 한 번 묻는다(`--start`의 `묻기:` 줄. 시작 질문에 묶어 멈춤을 늘리지 않는다). 둠은 `--hook`, 안 함은 `--unhook`이고 답은 프로젝트 설정 `git 훅 경고`에 남아 다시 묻지 않는다. `안 함`이면 다시 두지 않고, 뒤에 `--unhook`으로 지울 수 있다. `pre-commit`은 지키는 경로를 고치는 커밋에 경고만 한다. 사용자 훅은 바이트로 가려 덮지 않고, 있으면 두지 않고 알린다 |
| 실행 시작 | `--start`가 `확인 필요` 줄을 낸다. 메인이 한 줄로 알리고 낡음은 묻지 않는다 |
| 실행 중 | 판정자 공통 「낡은 문서」 |
| 실행 끝 | `--stale`. `run-end.md` 순서 2 뒤에 묻고, 답이 없어도 닫는다 |

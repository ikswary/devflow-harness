# 기획 정본 작성법

읽는 kind: `brief`.

기획의 목적은 개요가 묶음별 한 줄로 쪼갠 요구사항을 **사용자가 겪는 순서(여정·화면 흐름)와 동작을 가르는 규칙(정책)**으로 한 번에 묶어, 사람이 한 화면에서 짚고 상세·화면 설계·설계가 그대로 받게 하는 것이다. 개요가 승인된 뒤에 쓴다. 상세는 여기의 정책을 FR·AC로 옮기고 정책 id를 단다. 여기서 개요 범위 밖의 것을 깔고 쓰면 뒤에서 범위와 어긋난다 — 그런 것은 「정해 주실 것」이다.

## 좋은 기획의 조건

- 여정은 계기와 끝 상태가 있어야 한다. 단계마다 화면 id(또는 "화면 없음")와 개요 요구사항 번호를 단다. 어느 여정에도 안 들어가는 요구사항은 범위 밖·뒤 단계로 표시하거나 여정을 더한다.
- 화면 id는 소문자·하이픈(`plan-board`). 상세·화면 설계·설계·구현·시험이 같은 id를 쓴다. 「이번 변경」이 "기존 그대로"인 화면은 흐름을 보이려고 적는 것이고 화면 설계 대상이 아니다. 화면의 요소·배치·문구는 적지 않는다(ui-spec).
- 정책은 "값·조건·예외"가 다 있어야 정책이다. 개요 범위 밖의 정책은 깔고 쓰지 않고 「정해 주실 것」에 올린다. 상세가 정책마다 FR·AC를 쓰므로 정책은 FR의 초안이 아니라 **규칙의 목록**이다(같은 말을 Given/When/Then으로 다시 쓰지 않는다).
- 지표는 세는 방법이 없으면 지표가 아니다. 사람이 직접 세는 지표는 그렇게 적는다. 세려고 기능을 더해야 하면 그 기능은 범위 밖이거나 범위 변경 제안이다.
- 개요가 범위 안으로 둔 것을 뒤로 미루는 것은 사용자 결정이다. 근거(지금 만들 수 없다 / 실물이 있어야 한다 / 먼저 써 봐야 기준이 생긴다)를 쓴다.
- 기존 제품의 부분 변경(웹 사이트 한 구역 수정 등)은 바뀌는 여정 단계·화면만 적고 나머지는 "기존 그대로"다. 전체 여정을 새로 쓰지 않는다.
- 사용자가 말하지 않은 것을 채우면 표시한다. 사용자는 그것이 가정인 줄 모르고 승인한다.
- 정하지 않는 것: 인수 기준의 문장(requirements-spec), 화면 요소·배치·문구(ui-spec), 저장 형식·구성 요소(design-doc).

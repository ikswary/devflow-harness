# 배포 계획 task: 운영 브랜치 옮기기 (프로젝트 설정에 `운영 브랜치`가 있을 때)

읽는 때: 프로젝트 설정에 `운영 브랜치`가 있는 실행의 배포 계획 task를 쓰거나 판정할 때.

운영에 올린 코드만 운영 브랜치에 있게 하는 프로젝트 규칙을 지키려는 것이다. 운영에는 지금처럼 dev에서 확인한 커밋 C를 배포 폴더에서 올리고, **결과 승인이 `유지`일 때만** 운영 브랜치를 C로 앞감기한다. 병합 커밋을 만들지 않는 이유: 원래 폴더는 개발 기준 브랜치를 꺼내 두어 거기서 병합할 수 없고, 병합 커밋은 계획 때 해시를 알 수 없어 "같은 커밋" 대조가 깨지며, 병합을 배포보다 먼저 하면 실패·되돌림 때 배포되지 않은 코드가 운영 브랜치에 남는다. 환경별 설정은 브랜치가 아니라 설정 파일의 환경 절과 저장소 밖 비밀값으로 나뉘어 있어야 한다.
- 운영 배포 계획에서만 한다. 사전 조건에 "운영 브랜치가 C의 조상이다"(`git merge-base --is-ancestor {운영 브랜치} {C}`, 종료 코드 0)와 계획 때 운영 브랜치의 해시 O를 적는다. 조상이 아니면(운영 브랜치에만 있는 커밋) 계획을 쓰지 않고 「정해 주실 것」으로 올린다.
- 명령 목록 끝에 **`[유지 뒤]`** 표시를 붙여 적는다: `git -C {원래 폴더} update-ref refs/heads/{운영 브랜치} {C 전체 해시} {O 전체 해시}`(작업 트리를 건드리지 않는다. O가 아니면 실패하므로 그 사이 운영 브랜치가 움직였으면 멈춘다), 설정이 `운영 브랜치 push: 예`면 `git -C {원래 폴더} push origin {운영 브랜치}`. 계획 승인이 이 명령의 승인이고, 실행은 배포 실행의 결과 승인 `유지` 뒤다(`references/kinds/deploy-exec/main-order.md` 5의 다음).
- 프로젝트의 운영 브랜치 규칙 절이 "병합 방법은 그때 정한다"처럼 비어 있거나 병합을 적고 있어도, 그 절은 「배포 뒤 적을 문서」로 고치지 않는다. 적을 값("유지 뒤 앞감기")은 배포 결과가 아니라 계획 때 이미 알고, 그 문서는 배포 도구가 읽는 문서일 수 있기 때문이다(`references/kinds/deploy-plan.md` 「하는 일」 8과 같은 이유). 설계가 있는 실행이면 설계가 운영 브랜치 규칙 절의 수정을 문서 구현 task 범위에 넣는다. 배포만으로 시작한 실행이면 「정해 주실 것」에 올린다: (가) 배포 전에 문서를 고치는 변경을 먼저 한다 / (나) 문서는 그대로 두고 배포하고, 문서와 하네스 방식이 어긋난다는 것을 「알릴 것」에 적는다.

「자체 검증」에 더하는 것:
10. 프로젝트 설정에 `운영 브랜치`가 있고 운영 계획이면: 사전 조건에 조상 확인과 O가 있고, `[유지 뒤]` 명령이 `update-ref`(새 값 C, 예전 값 O)와 설정대로의 push뿐이며, 원래 폴더의 작업 트리를 바꾸는 명령(checkout, switch, merge)이 없다(판정자가 `git merge-base --is-ancestor`와 `git rev-parse`로 확인).

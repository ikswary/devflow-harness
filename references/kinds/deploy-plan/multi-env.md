# 배포 계획 task: 환경이 둘 이상일 때 (계획은 동시에, 실행은 차례로, 운영은 dev에서 확인한 커밋 그대로)

읽는 때: 배포 환경이 둘 이상(dev와 운영)인 실행의 배포 계획 task를 쓰거나 판정할 때.

dev와 운영의 배포 계획은 함께 쓰고 각각 승인받는다. 운영 계획의 승인을 dev 배포가 도는 동안 미리 받아 두어, dev가 끝나면 바로 운영으로 가려는 것이다.
- **같은 커밋**: 뒤 환경(운영)은 앞 환경(dev) 계획과 같은 커밋을 올린다. 두 계획 모두 마무리 머리 파일의 `exported_commit`을 「올릴 것」으로 쓰므로 앞 환경 계획의 결과를 읽지 않는다(같은 커밋 보증은 배포 실행 사전 조건의 `deployed_commit` 대조가 한다). 앞 환경 배포 뒤에 개발 기준 브랜치에 들어간 배포 기록 문서는 운영에 올라가지 않는다(다음 배포 때 들어간다). 문서만 바뀌어도 배포 동작이 달라지는 프로젝트가 있고, 빌드 식별자가 커밋 해시인 프로젝트에서는 맞춘 폴더의 빌드를 계획의 커밋과 대조할 수 없기 때문이다.
- **사전 조건 맨 앞**: "앞 환경 배포 실행 task의 머리 파일이 `deploy_outcome: 유지`, `deployed_commit`이 이 계획의 커밋, 배포 뒤 확인이 모두 통과했거나 통과하지 못한 확인마다 결과 승인 기록에 사용자가 받아들인 위험으로 적혀 있음, 사람이 볼 확인마다 사용자의 답이 있음(위임이면 `references/kinds/deploy-exec.md` 「사람 확인의 위임」대로 확인자와 「확인 안 된 것」이 적힌 기록)". 받아들인 위험과 위임으로 확인 안 된 항목은 「알릴 것」에 옮긴다.
- **의존**: 뒤 환경의 배포 실행 행은 앞 환경의 배포 계획 task에 `depends_on`으로 의존한다(그 id는 메인이 머리 파일 「범위」에 적는다. 앞 환경의 배포 실행 task는 아직 없어 행에 적을 수 없다). 메인이 앞 환경의 배포 실행 task를 만드는 같은 단계에서 그 id를 뒤 환경 배포 실행의 `depends_on`에 더한다.
- 앞 환경에서 코드를 고치게 되면 이 계획은 낡는다. 메인이 「배포 다시 계획」으로 처리한다.

「자체 검증」에 더하는 것:
9. 뒤 환경이면 사전 조건 맨 앞에 앞 환경 실행의 유지·같은 커밋·확인 통과(또는 받아들인 위험)·사람 확인 답이 있고, 배포 실행 행이 앞 환경 배포 계획에 의존한다.

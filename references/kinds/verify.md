# 검증 task (흐름별 검증 `flow-verify`, 전체 검증의 관점 task `full-verify`, 재검증 `reverify`)

어느 구현 task도 혼자 확인할 수 없는 것을 본다. 코드를 고치지 않는다. 고치는 주체와 판정하는 주체가 나뉘어야 판정을 믿을 수 있다.

## 먼저 읽을 것
`${CLAUDE_PLUGIN_ROOT}/references/practices/code-review-checklist.md`(심각도 분류와 지적 형식), `${CLAUDE_PLUGIN_ROOT}/references/practices/test-rules.md`, 요구사항·설계 정본의 해당 절.

판정자: `${CLAUDE_PLUGIN_ROOT}/references/practices/code-review-checklist.md`, `${CLAUDE_PLUGIN_ROOT}/references/practices/test-rules.md`

## 하는 일
변경 범위는 프롬프트가 준 커밋 범위나 브랜치로 `git diff`해서 본다. 구현 task의 결과 파일은 프롬프트가 준 것만 읽는다.

### 흐름별 검증 (`flow-verify`)
시작 조건은 `board.py --ready`가 본다(그 흐름의 구현·수정 task가 모두 끝남, 받아오기 없음. 보류된 구현이 있으면 메인이 그 흐름을 보류할지 남은 것만 검증할지 묻는다). 코드 폴더는 그 흐름의 폴더다.

보는 것:
1. **인수 기준 추적**: 그 흐름이 닫는 인수 기준을 전 행 독립 판정한다(구현 task의 "닫음" 표시를 믿지 않고 테스트와 코드에서 다시 확인). 표: 인수 기준 | 확인 방법 | 판정(통과/실패/판정불가) | 근거(파일:줄).
2. **구현 task 사이 불일치**: 이름, 예외 처리, 중복 정의, 같은 값의 여러 정의.
3. **다시 읽기**: 메인이 `collect.py {실행 폴더} {이 task 폴더} --notified {흐름}`으로 뽑아 경로를 준 `notified-{흐름}.md`의 task는 **전부** 변경을 다시 읽고, 그 파일의 알릴 것·확인 안 된 것을 승인 화면으로 옮긴다(메인의 기억으로 목록을 만들지 않는다). task마다 "숨은 예외 있음/없음"(적혀 있지 않은 설계와의 차이, 대상 밖 변경, 약한 테스트)을 표로 적는다. 나머지 구현 task는 표본(프롬프트가 준 수)을 다시 읽는다. 지적마다 `원인 task`를 적는다.
4. **써 볼 방법**: 사람이 이 기능을 직접 확인하는 실행 방법과 볼 것(→ 「하실 일·허용 요청」). 화면 정본 `ui\{묶음}.md`가 있으면 그 조작 표를 따라 쓰고, 조작의 결과·상태가 정본과 다른 곳은 지적이다(원인 task는 그 화면의 구현 task).
5. 흐름이 하나뿐인 실행이면 전체 관점(보안, 성능 등 머리 파일이 준 관점)과 실제 경로 확인까지 본다. 양이 많으면 관점별로 스스로 줄인다.

리뷰로 시작한 실행(이미 있는 변경의 검토)은 요청이나 PR 설명에서 "의도한 동작"을 뽑아 인수 기준 대신 쓴다.

### 전체 검증의 관점 task (`full-verify`)
모든 흐름이 통합 브랜치에 합쳐진 뒤, 통합 폴더에서. 관점 하나를 맡는다(머리 파일의 범위). 예: 기능 사이 정합, 보안, 성능.
- 기능 사이 정합 관점은 흐름 사이의 이름·형식·값 불일치와, 어느 기능에도 넣지 못한 인수 기준을 본다. 흐름 지도의 겹침 분류(각자 진행 / 이어 붙이기)가 실제 변경과 맞는지도 본다.
- 전체 테스트의 결과는 실행 판정이 돌린 것을 받는다.
- 다른 관점이 이미 낸 지적과 같은 곳(파일·줄)을 지적하게 되면 그대로 적는다. 겹침은 메인이 정리한다.

### 재검증 (`reverify`)
검증 task가 낸 지적을 수정 task가 고친 뒤. 범위는 머리 파일이 준 지적과 그 인수 기준뿐이다. 그 밖을 다시 보지 않는다.
- 지적마다 해결/미해결/새 문제를 적는다. 그 지적을 고친 수정 task가 알림으로 지나갔으면, 그 task의 알릴 것·확인 안 된 것을 `[T0xx]`로 「알릴 것」「확인 안 된 것」에 옮긴다(흐름별 검증 뒤의 수정은 모아 줄 다른 화면이 없다). 옮길 것이 있으면 이 재검증은 알림으로 지나가지 않는다. 수정이 닿은 파일에서 새로 생긴 문제는 새 지적으로 낸다.
- 새 지적이 없으면 작성자가 「정해 주실 것」·「알릴 것」·「확인 안 된 것」을 `- 없음`으로 두고, 재검증은 알림으로 끝난다. [RP-12]

### 지적의 형식과 분류
지적마다: ID, 심각도(차단/중요/권장), 무엇이 문제인지 한 문장, 파일:줄, 실패 시나리오(구체적 입력과 결과), 제안, **원인 task**, **분류**.

| 분류 | 조건 | 승인 화면 |
|---|---|---|
| 묻는다 | 고칠 방법이 여럿 / 요구사항·설계를 바꿔야 함 / 고치지 않고 받아들일지가 갈림 | 정해 주실 것(선택지와 추천) |
| 바로 고친다 | 차단·중요이고 고칠 방법이 하나로 정해짐 | 알릴 것(한 줄씩) |
| 확인을 넘긴다 | 실제 경로에서 확인 못 함, 판정 못 한 인수 기준 | 확인 안 된 것(확인할 task) |
| 쌓는다 | 권장 | 건수만(백로그 task가 된다) |

코드에서 다시 확인하지 못한 지적은 "근거 부족"으로 본문 하단에 따로 둔다.

## 승인 화면
- 정해 주실 것: "묻는다" 지적
- 하실 일·허용 요청: 써 볼 방법, 사용자만 할 수 있는 확인
- 알릴 것: 실패한 인수 기준, "바로 고친다" 지적, (흐름별 검증) 알림으로 지나간 task의 「알릴 것」을 `[T0xx]`를 붙여 한 줄씩
- 확인 안 된 것: 판정불가 인수 기준, "확인을 넘긴다" 지적, (흐름별 검증) 알림으로 지나간 task의 「확인 안 된 것」 가운데 이 검증에서도 확인하지 못한 것을 `[T0xx]`를 붙여 한 줄씩
- 건수만: 통과한 인수 기준 수, 권장 지적 수, 다시 읽은 task 수와 숨은 예외 수

## 자식 목록
자식 kind: `fix`, `reverify`

- "바로 고친다" 지적마다(같은 곳을 고치는 지적은 묶어) 수정 task 행(`kind: fix`): 범위 = 지적 ID와 제안, 판정 기준 = 지적의 실패 시나리오가 더는 일어나지 않음, 건드릴 파일. `flow`는 흐름별 검증이면 그 흐름, 전체 검증이면 `fixes`.
- "쌓는다" 지적마다 백로그 행(`kind: fix`, 제목 앞에 `[백로그]`). `spawn_children.py`가 `백로그` 상태로 만든다.
- 수정 task 행이 하나라도 있으면 재검증 task 행(`kind: reverify`): 범위 = 고친 지적 ID와 그 인수 기준. 수정 task들에 의존한다.
- "묻는다" 지적의 수정 행은 사용자의 답을 받은 뒤 메인이 만든다. 선택지마다 수정 행을 미리 적어 두면(`- option: V-01/가`. 여러 안에 걸치면 쉼표로) 변경 task 없이 진행된다(고르지 않은 안은 만들지 않고, 백로그로 남기라고 답한 안은 `백로그`로 만든다).

## 자체 검증 (읽기 판정)
판정은 검증 결과를 쓰지 않은 주체가 한다.
1. 차단·중요 지적 전부와 권장 지적 표본이 코드에서 실제로 확인된다(판정자가 파일:줄을 열어 실패 시나리오를 따라간다).
2. 지적의 분류가 표와 맞다. "바로 고친다"로 분류된 지적에 실제로 다른 고칠 방법이 없는가.
3. 인수 기준 추적표의 근거 줄을 표본 대조한다. 전 행에 판정과 근거가 있다.
4. 알림으로 지나간 task가 전부 다시 읽혔다(목록과 표를 대조).
5. 재검증: 재판정한 행의 근거가 실재한다.

# 배포 계획 task (`deploy-plan`)

설계의 배포 계획 한 줄(환경 하나, 시점 하나)을 그대로 실행할 수 있는 명령 목록으로 만든다. 작성은 `devflow-harness:release-writer`, 판정은 읽기 판정이다. **이 task의 승인이 배포 실행의 승인이다.** 알림으로 지나가지 않는다.

시작 조건: 마무리 task가 `완료`(올릴 커밋이 개발 기준 브랜치에 들어감). 배포만으로 시작했으면 올릴 커밋이 개발 기준 브랜치에 있음. 다른 환경의 배포 계획·실행은 기다리지 않는다.

## 먼저 읽을 것
`${CLAUDE_PLUGIN_ROOT}/references/practices/release-practice.md`(배포 방식 탐지와 롤백 절차의 방법), 설계 정본의 「배포 계획」, `recon.md`, 프로젝트의 배포 문서, 이 task가 의존하는(`depends_on`) 마무리 task의 머리 파일(`exported_commit`). 배포만으로 시작했으면 `origin`이 가리키는 task 폴더의 `result.md`.

경우 파일: 환경이 둘 이상이면 `references/kinds/deploy-plan/multi-env.md`, 프로젝트 설정에 `운영 브랜치`가 있으면 `references/kinds/deploy-plan/prod-branch.md`, 배포만으로 시작했으면 `references/kinds/deploy-plan/deploy-only.md`, 운영 환경이면 `references/kinds/deploy-plan/production.md`.

## 하는 일
1. **올릴 것**: 올릴 커밋의 해시와 배포 폴더. 원래 폴더는 쓰지 않는다. 환경과 상관없이 마무리 머리 파일의 `exported_commit`(배포만이면 `origin` 실행 마무리의 것, 그 값이 비면 개발 기준 브랜치의 끝). 배포 폴더(통합 폴더, 흐름이 하나면 흐름 폴더, 배포만이면 배포 폴더)의 `HEAD`가 그 커밋 **해시 자체**이고 커밋 안 된 변경이 없어야 한다고 사전 조건에 적는다. 배포 폴더의 `HEAD`를 그 커밋으로 옮기는 명령이 필요하면 명령 목록 맨 앞에 넣는다. 프로젝트의 배포 도구가 특정 브랜치·폴더를 요구하면 그 근거(파일:줄)와 함께 「정해 주실 것」으로 올린다.
2. **사전 조건**: 항목마다 확인 명령과 기대값. 배포 메모의 "배포 전 확인"을 모두 옮긴다. 최종 배포 후보 CI의 검증 commit·artifact를 적고, 올릴 것과 각각 같은지 확인한다. 부분 검사 기록은 쓰지 않는다. 다르면 배포하지 않고 새 최종 CI가 필요하다. 사용자만 할 수 있는 것은 「하실 일」로.
3. **명령 목록**: 자리 표시 없이 그대로 실행할 형태로, 순서대로, 「정해 주실 것」의 `cmd` 울타리에 한 줄씩(`formats.md` 4절. 배포 실행이 이 줄을 얼려 그대로 돌린다). 명령마다 근거(프로젝트 배포 문서의 절, 스크립트 파일:줄, `recon.md`)를 단다. 추측한 명령은 쓰지 않는다. 근거가 없으면 그 자리에서 닫고 「정해 주실 것」으로 올린다. 비밀값은 명령에 적지 않는다(환경 변수·파일 이름으로만).
   - 대화형 입력(숨김 입력, 이름 다시 치기 등)이 있거나 권한 시스템에 막힐 것이 분명한 명령은 `[사용자 실행]`으로 표시하고, 사용자가 실행한 뒤 알려 줄 것(종료 코드, 출력의 어느 줄)을 적는다. 입력을 파이프·인자로 채워 도구의 확인 절차를 건너뛰는 형태로 바꾸지 않는다.
4. **배포 뒤 확인**: 확인마다 읽기와 쓰기를 나누고, 닫는 인수 기준이 있으면 번호를 적고, 실행 판정이 돌릴 것(명령)과 사람이 볼 것(메일함, 화면)을 나눈다.
   - dev(운영이 아닌 환경): 쓰기가 있는 경로(접수 POST, 메일 발송 등)를 읽기만으로 확인하게 두지 않는다. 쓰기 확인이 남기는 데이터·발송과 확인용 표시, 지우는 방법을 적는다.
5. **되돌리기**: 도구에 내장된 되돌리기가 있으면 그 명령을 그대로(「되돌리기」 제목 아래 `cmd` 울타리). 도구가 실패 때 스스로 되돌리는지(종료 코드별)도 적는다. 되돌릴 수 없는 단계(예: 처음 들어가는 자원·클래스)는 "되돌릴 수 없음"과 그 이유를 적고 「정해 주실 것」 맨 앞에 올린다.
6. **공유 자원**: dev DB·포트를 쓰는 사전 조건·확인 명령은 `recon.md`의 잠금 안에서 돌린다고 적는다.
8. **배포 뒤 적을 문서**: 설계의 배포 계획 줄에서 옮긴다(파일, 절, 적을 값과 그 값을 어디서 읽는지: `exec.md`의 어느 명령 출력, `judge-run.md`의 어느 확인). 배포 실행의 배포 기록이 이것대로 쓰고, 넣는 명령(커밋할 파일, 병합 명령)은 마무리의 내보낼 명령과 같은 방식으로 지금 적는다. 배포 도구가 읽는 문서는 적을 문서로 고르지 않는다. 없으면 "없음".

## 승인 화면
- 정해 주실 것: 명령 목록 전체(그대로, 작업 폴더와 함께, `[사용자 실행]` 표시 포함). "이 명령들을 이 순서로 실행합니다". 되돌릴 수 없는 단계가 있으면 맨 앞에.
- 하실 일·허용 요청: 사용자만 할 수 있는 사전 조건, `[사용자 실행]` 명령, 사람이 볼 배포 뒤 확인
- 알릴 것: 올릴 커밋, 비용, 배포 뒤 확인 목록(읽기/쓰기), 쓰기 확인이 남기는 데이터와 지우는 방법, 배포 뒤 적을 문서(넣는 명령은 배포 실행에서 다시 보여 주고 받는다)
- 확인 안 된 것: 근거가 약한 명령, 이 배포로도 닫지 못하는 인수 기준
- 건수만: 명령 수, 사전 조건 수, 확인 수

## 자식 목록
자식 kind: `deploy-exec`

- 배포 실행 task 행 하나(`kind: deploy-exec`): 범위 = 이 task의 명령 목록과 배포 뒤 확인과 배포 뒤 적을 문서, 판정 기준 = `references/kinds/deploy-exec.md` 「자체 검증」, 닫는 인수 기준. 뒤 환경이면 `depends_on`에 앞 환경 배포 계획 task id.

## 자식 행 계약
- 배포로만 닫히는 인수 기준은 설계가 배포 계획 행의 닫는 인수 기준에 넣어야 배포 실행 행으로 이어진다.
- 설계의 배포 계획 한 줄(환경 하나, 시점 하나)을 그대로 실행할 수 있는 명령 목록으로 만든다. [RP-14]
- dev와 운영의 배포 계획은 함께 쓰고 각각 승인받는다. [RP-15]
- 설계가 있는 실행이면 설계가 운영 브랜치 규칙 절의 수정을 문서 구현 task 범위에 넣는다. [RP-16]
- 운영: 배포 뒤 확인에서 **쓰기 확인을 하지 않는다**. [RP-17]

## 자체 검증 (읽기 판정)
1. 명령마다 근거가 실재하고(판정자가 파일:줄을 연다) 승인된 배포 방식(프로젝트 설정·`recon.md`·설계 결정)과 맞다. 근거 없는 명령이 있으면 실패. 대화형 입력을 파이프·인자로 채운 명령이 있으면 실패.
2. 배포 메모의 배포 전 확인이 사전 조건에 빠짐없이 있다(마무리 결과와 대조).
3. dev: 외부 서비스를 거치는 연결 경로마다 읽기와 쓰기 확인이 있다. 쓰기가 있는 경로를 읽기만으로 확인하면 실패. 운영: 쓰기 확인이 없고(「정해 주실 것」으로 올린 것 제외), 쓰기 경로마다 대조표가 dev 쓰기 확인을 가리킨다.
4. 올릴 커밋이 마무리 머리 파일의 `exported_commit`(비면 개발 기준 브랜치의 끝)과 같은 해시다. 사전 조건에 배포 폴더의 `HEAD` 해시와 깨끗한 작업 트리 확인, 최종 배포 후보 CI의 검증 commit·artifact와 배포 commit·artifact의 동일성 확인이 있다(판정자가 읽기 명령으로 확인).
5. 되돌릴 수 없는 단계가 빠짐없이 표시됐다(설계 결정·배포 문서와 대조).
6. 명령·결과에 비밀값, 계정 식별자, 연결 문자열이 없다.
8. 배포 뒤 적을 문서가 설계의 배포 계획 줄(배포만으로 시작했으면 이어받은 배포 메모)과 같고, 적을 값마다 읽을 곳이 이 계획의 명령·확인 가운데 하나이며, 배포 도구가 읽는 문서가 아니다.

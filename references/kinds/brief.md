# 기획 task (`brief`)

요구사항 개요 뒤, 요구사항 상세 앞에 오는 실행 하나짜리 task다(흐름 없음, 개요에 의존). 요구사항 블록이 있는 실행(새 기능, 기능 변경)에는 늘 있다. 개요가 정한 범위·묶음·요구사항 한 줄·용어를 받아 **사용자 여정·화면 흐름, 정책·규칙·예외, 우선순위·범위 밖·단계, 목표·성공 지표**를 한 번에 짚고, 상세·화면 설계·UI 규약 행을 만든다. 인수 기준(FR/AC)은 상세의 일이고(상세가 기획의 정책을 FR로 옮긴다), 화면의 요소·배치·문구는 화면 설계의 일, 구성 요소·데이터는 설계의 일이다.

## 먼저 읽을 것
`${CLAUDE_PLUGIN_ROOT}/references/practices/product-brief.md`, 정본 `spec\overview.md`(범위·묶음 지도·요구사항 한 줄·「용어」), 부모(개요) 머리 파일의 승인 기록과 질문 task의 답, `decisions.md`, `recon.md` 「UI 규약」, 머리 파일 「범위」가 가리키는 그 밖의 경로(README, 받은 화면 캡처 등). 다시 열거나 더한 실행이면 앞 회차의 `spec\brief.md`(있으면)도 읽되, 범위는 이번 회차 묶음만이다.

## 하는 일
1. 결정 지도를 먼저 쓴다(`writer.md` 2절). 답이 없는 사용자 결정(정책의 값, 우선순위의 경계)에 나머지가 의존하면 거기서 닫는다. 스스로 줄여야 하면 **화면 흐름과 자식 목록을 먼저 닫고** 정책·지표를 뒤 자식으로 넘긴다(자식 행이 늦어지면 상세·화면 설계가 모두 기다린다).
2. 정본 `spec\brief.md`를 쓴다(다시 연 실행은 `## 회차 {n}` 절을 더한다. 앞 회차 절은 고치지 않는다).
   - **사용자 여정·화면 흐름**: 여정마다 행위자·계기·단계·끝 상태, 단계마다 닿는 개요 요구사항 번호. 화면 목록(화면 id·이름·묶음·목적·**이번 변경**: 새로 그림 / 부분 변경 / 기존 그대로)과 이동 표. 화면 id는 상세·화면 설계·설계·구현이 그대로 쓴다. 요소·배치·문구는 적지 않는다. 기존 화면의 부분 변경이면 바뀌는 단계·화면만 적고 나머지는 "기존 그대로".
   - **정책·규칙·예외**: 동작을 가르는 규칙(값·조건·예외·실패 때 동작)을 정책 id(`P-{n}`)와 개요 요구사항 번호로. 상세가 정책마다 FR·AC를 쓰고 정책 id를 단다. 개요 범위 밖의 정책이 필요하면 깔고 쓰지 않고 「정해 주실 것」(범위를 바꾸는 제안).
   - **우선순위·범위 밖·단계**: 개요 요구사항 단위로 이번 실행 / 뒤 단계 / 범위 밖. 개요가 범위 안으로 둔 것을 뒤로 미루는 것은 사용자 결정이다(「정해 주실 것」). 다시 연·더한 실행은 앞 회차에 "이미 있음" 표시. 단계마다 근거.
   - **목표·성공 지표**: 목표는 결과 상태 문장, 지표마다 세는 방법(앱 기록·파일·사람이 직접 셈). 측정 수단이 새 기능이 되면 범위 밖이거나 범위 변경 제안이다.
3. 사용자가 말하지 않았는데 정한 것(여정의 경계, 정책 값, 지표 기준값, 단계 경계)은 "담당이 채움"으로 표시한다(「정해 주실 것」에 올린 것은 제외).
4. 실물·실제 데이터로 확인하지 않은 전제는 「확인 안 된 것」에 올리고 확인할 task를 적는다.
5. 묶음마다 화면 유무를 정한다: 화면 목록에 그 묶음의 화면이 있고 이번 변경이 "새로 그림"이나 "부분 변경"이면 화면 있음. 화면이 하나뿐이고 상태·조작이 단순하면 화면 설계 행을 두지 않을 수 있다(「알릴 것」에 이유. 그때 설계 「화면」 절이 요소·상태·조작·문구까지 쓴다).

## 승인 화면
- 정해 주실 것: 개요 범위 밖의 정책, 범위 안을 뒤로 미루는 것, 정책 값·지표 기준값처럼 사용자만 아는 값, 서로 부딪치는 여정
- 알릴 것: 담당이 채운 것, 화면 있음/없음으로 가른 묶음과 이유, 화면 설계 행을 두지 않은 화면 묶음과 이유, UI 규약 행을 둔 이유(또는 두지 않은 이유)
- 확인 안 된 것: 실물·실제 데이터로 보지 않은 전제(틀리면 바뀌는 것, 확인할 task)
- 건수만: 여정 수, 화면 수(새로 그림/부분 변경/기존 그대로), 정책 수, 담당이 채운 항목 수

## 자식 목록
자식 kind: `req-detail`, `ui-design`, `design`

- **상세 행**(`kind: req-detail`): 묶음마다 하나(규칙은 `references/kinds/req-overview.md`가 정하던 것과 같다 — `common`이 있으면 다른 상세는 그것에 의존하지 않고, 결과를 쓰는 쪽 묶음은 의존하는 묶음의 상세에 `depends_on`). 범위에 "기획 정본의 이 묶음 정책 id와 화면 id"를 적는다. 개요가 상세를 겸했으면(묶음 하나, `references/kinds/req-overview.md` 5) 상세 행을 쓰지 않고 그 묶음의 설계 행(`kind: design`, 화면 설계 행이 있으면 그것에 의존)을 대신 쓴다.
- **UI 규약 행**(`kind: ui-design`, 제목 `화면 설계 — UI 규약`, 흐름 없음): 실행 폴더에 `ui\rules.md`가 없고 화면 목록에 "새로 그림"인 화면이 있을 때만 하나. 범위 = `recon.md` 「UI 규약」과 개요 「용어」, 건드릴 파일 = `ui/rules.md`, 판정 기준 = `references/kinds/ui-design/rules-task.md`. 부분 변경만 있는 실행은 두지 않는다(화면 설계가 기존 스타일 위치를 가리킨다).
- **화면 설계 행**(`kind: ui-design`, `flow`는 묶음 이름): 화면 있는 묶음마다 하나(5의 예외 제외). `depends_on` = 그 묶음의 상세 행 제목과 UI 규약 행 제목(있으면). 범위 = 그 묶음의 화면 목록(화면 id·이번 변경)과 상세 정본, 판정 기준 = `references/kinds/ui-design.md` 「자체 검증」, 건드릴 파일 = `ui/{묶음}.md`, `ui/wireframes/{묶음}.html`, 정본의 절 = `spec\brief.md` 「화면 흐름」의 그 묶음 줄과 `spec\{묶음}.md`.
- 설계 행은 상세가 쓴다(화면 묶음이면 그 화면 설계 task에 의존하게. 메인이 상세 프롬프트에 화면 설계 task id를 준다). 여기서 쓰지 않는다.

## 자체 검증 (읽기 판정)
원 산출물은 머리 파일 「건드릴 파일」의 `spec\brief.md`(다시 연 실행은 이번 회차 절), 대조 원천은 `spec\overview.md`(범위·묶음 지도·요구사항 번호·「용어」)와 질문·개요의 승인 기록이다.
1. 개요의 이번 회차 요구사항 번호마다 어느 여정의 단계에 있거나 범위 밖·뒤 단계로 표시됐다(판정자가 개요 번호 집합과 기획이 인용한 번호 집합을 `grep`으로 뽑아 대조. 없는 번호를 인용했으면 실패).
2. 화면 목록의 모든 화면이 이동 표에서 닿고, 여정의 단계마다 화면 id(또는 "화면 없음")가 있다.
3. 정책마다 id·값·조건·예외 칸이 비어 있지 않고 개요 요구사항 번호가 있거나 「정해 주실 것」에 있다.
4. 지표마다 세는 방법이 있다(사람이 직접 센다도 세는 방법이다). "효율적으로·편하게·빠르게"가 지표에 남아 있으면 실패.
5. 담당이 채운 것이 빠짐없이 「알릴 것」에 있다(판정자가 정본의 경계·값·기준값을 요청 원문·답·개요에서 찾아 본다. 「정해 주실 것」에 올린 것은 제외).
6. 인수 기준(Given/When/Then), 화면의 요소·배치·문구, 구성 요소·저장 형식을 정한 문장이 없다(화면 목록과 이동 표는 허용).
7. 자식 목록 집합 대조: 상세 행의 묶음 집합 == 개요 묶음 지도의 이번 회차 묶음 집합(개요가 상세를 겸했으면 설계 행 하나). 화면 설계 행의 묶음 집합 == 화면 목록에서 "새로 그림/부분 변경" 화면이 있는 묶음 집합 − 「알릴 것」에 예외로 적은 묶음. `ui\rules.md`가 없고 "새로 그림" 화면이 있으면 UI 규약 행이 있고 화면 설계 행이 모두 그것에 의존한다. 화면 설계 행마다 그 묶음의 상세 행에 의존한다.

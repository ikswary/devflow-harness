# 배포 실행 task (`deploy-exec`)

승인된 배포 계획의 명령을 **메인이** 순서대로 실행하고, 배포 뒤 확인을 실행 판정이 다시 돌린다. 부모(배포 계획)의 승인이 실행 승인이다. 알림으로 지나가지 않는다.

사람에게 가는 자리는 최대 셋이고 각각 작게 둔다: (운영만) 실행 직전 확인 → **결과 승인**(유지/되돌림만) → (배포 뒤 적을 문서가 있고 유지했을 때만) **문서 넣기 승인**. 유지/되돌림을 문서 작성·판정 뒤로 미루지 않는 것은, 확인이 실패한 운영이 그 사이 고장 난 채로 기다리지 않게 하려는 것이다. 배포 기록을 따로 task로 두지 않는 것은 문서 몇 줄에 구현·마무리 한 벌이 더 돌았기 때문이다.

## 하는 일
### 단계와 기록
머리 파일 `stage`에 지금 단계를 적고 단계가 바뀔 때마다 고친다: `사전조건` → `직전확인`(운영) → `명령` → `확인` → `결과승인` → `브랜치`(운영 브랜치 옮기기가 계획에 있을 때) → `기록` → `넣기승인` → `넣기` → `끝`(묻는 단계는 `승인대기`, 그 밖은 `진행`). 재개 때 메인은 이 값과 `exec.md`로 어디서 이어 갈지 정한다. 결과 승인 뒤에 `deploy_outcome`(유지/되돌림/보류)와 `deployed_commit`(올라간 커밋)을 적는다. 시작(`대기→진행`) 때 `task_set.py`가 부모 계획의 명령(`실행승인`)과 되돌리기(`되돌림`)를 얼린다. 부모 계획에 `cmd` 울타리가 없어 얼리지 못했으면(옛 형식 계획) 명령을 돌리지 않고 「배포 다시 계획」으로 새 형식의 계획을 받는다.

6. **배포 기록**(결과 승인 뒤 늘 한다. 유지/되돌림은 이미 정해졌으니 이 단계가 그 판단을 늦추지 않는다): 메인이 `devflow-harness:release-writer`를 `release-{id}`로 띄운다. 입력은 경로로: 이 머리 파일(승인 기록 포함), 부모 계획의 결과, `exec.md`, `judge-run.md`. 작성자는 이 task의 `result.md`(`formats.md` 4절. 「승인 화면」은 결과 승인 때 보인 것과 답, 「확인 안 된 것」은 다음 마무리의 배포 메모가 `collect.py`로 모은다)를 쓴다. 유지이고 계획의 배포 뒤 적을 문서가 "없음"이 아니면 배포한 폴더에서 계획이 정한 문서 절만 고치고(커밋하지 않음), 적은 값마다 읽은 곳(`exec.md`의 줄, `judge-run.md`의 확인)을 `result.md`에 적고, 커밋 메시지와 넣는 명령을 계획대로 적는다. 실패한 확인은 실패로 적는다. 값은 `exec.md`·`judge-run.md`·머리 파일 승인 기록에서만 옮기고 거기 없는 값은 「확인 안 된 것」에 둔다. 계정 식별자·호스트명은 옮기지 않는다. 읽기 판정(`rjudge-{id}`)이 `result.md`의 확인 결과가 `judge-run.md`와 같은지와, 문서를 고쳤으면 아래 자체 검증 6·7을 보고, 메인이 8을 돌린다. 고친 문서가 없으면 `references/kinds/deploy-exec/main-order.md` 순서 7·8(넣기 승인·넣기)을 건너뛰고 `stage: 끝`.

### 사람 확인의 위임 (받되 제한)
사용자가 사람이 볼 확인을 맡기면("니가 알아서 해") 받되, 맡긴 것은 확인이지 새 실행이 아니다.
- 위임은 새 명령·쓰기를 허락하지 않는다. 계획에 없는 명령·쓰기가 필요하면 명령을 그대로 보여 주고 따로 승인받는다. 운영에서는 위임이 있어도 쓰기를 하지 않는다.
- 도구로 볼 수 있는 항목(발송 기록 조회, 로그, DB 읽기)은 메인이 아니라 실행 판정자(`xjudge-{id}`)에게 그 항목을 확인 목록으로 주어 돌린다. 결과는 `judge-run.md`에 남는다.
- 도구로 볼 수 없는 것(실제 받은편지함 화면, 눈으로 보는 품질 판단)은 대신 확인했다고 적지 않고 「확인 안 된 것」에 둔다.
- 승인 기록에 `위임`과 원문, 항목마다 확인자(xjudge / 확인 안 됨)를 적는다. 뒤 환경 사전 조건이 이 기록을 본다(`references/kinds/deploy-plan/multi-env.md`).

## 승인 화면
결과 승인(`references/kinds/deploy-exec/main-order.md` 순서 5):
- 정해 주실 것: 유지 / 되돌림 / 보류 (되돌릴 수 없는 배포면 그 사실과 대신 할 수 있는 것)
- 하실 일: 사람이 볼 배포 뒤 확인(메일함, 화면)
- 알릴 것: 실행한 명령과 종료 코드, 배포 뒤 확인 결과, 쓰기 확인이 남긴 데이터와 지우는 방법, 올라간 빌드
- 확인 안 된 것: 돌리지 못한 확인, 사용자 실행에서 알려 주지 않은 값, 닫지 못한 인수 기준
- 건수만: 실행한 명령 수, 통과한 확인 수

문서 넣기 승인(`references/kinds/deploy-exec/main-order.md` 순서 7):
- 정해 주실 것: 넣는 명령(그대로)
- 알릴 것: 고친 문서와 절, 적은 값과 읽은 곳
- 확인 안 된 것: 값을 찾지 못해 비워 둔 것

## 자체 검증 (실행 판정 + 읽기 판정: 조건)
1. `exec.py --verify` 통과(승인된 줄만 모두 돌고 종료 코드 0, 사용자 실행은 알려 준 결과, `[유지 뒤]`는 유지일 때만, 메인 실행). `judge-run.md`의 확인별 줄이 계획의 배포 뒤 확인 가운데 실행 판정 몫과 한 줄씩 같다(메인, "기록 대조").
2. 올라간 빌드가 계획의 커밋이다(배포 도구의 버전·태그·메시지로 실행 판정이 확인).
3. 배포 뒤 확인: 실행 판정이 돌린 결과. dev는 쓰기 확인이 실제로 쓰기를 했다(읽기만으로 통과시키지 않는다). 운영은 쓰기 확인이 돌지 않았다.
4. 맡은 인수 기준 판정(배포된 것으로만 판정되는 인수 기준을 이 task가 닫을 수 있다).
5. `logs\`, `exec.md`, `judge-run.md`에 비밀값·계정 식별자가 없다(메인, "메인 실행").
6. (배포 기록) 고친 파일과 절이 계획의 배포 뒤 적을 문서와 같고 그 밖을 고치지 않았다(메인이 `git diff --stat`, "기록 대조". 절 범위는 읽기 판정).
7. (배포 기록) 적은 값마다 `exec.md`·`judge-run.md`의 해당 줄과 같다. 실패한 확인을 통과로 적지 않았다. 계정 식별자·호스트명이 없다(읽기 판정이 하나씩 대조).
8. (배포 기록) 넣을 변경에서 비밀값 패턴 검색 0건(메인이 내보낼 브랜치의 비밀값 검색과 같은 검색을 넣을 변경에 돌림, "메인 실행").
9. (문서를 넣었으면) `exec.py --verify`의 넣기승인 지점 통과(병합 판정 포함, 메인 실행).
10. (운영 브랜치를 옮겼으면) 원래 폴더의 운영 브랜치가 `deployed_commit`이고, push했으면 `git ls-remote origin {운영 브랜치}`가 같은 해시다. 원래 폴더의 꺼낸 브랜치와 `git status`가 실행 전과 같다(메인, "메인 실행").

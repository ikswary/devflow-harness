# 구현 task (`implementation`), 수정 task (`fix`)

머리 파일이 정한 범위의 코드와 테스트를 쓴다. 검증 지적을 고치는 수정 task와 사용자 답으로 코드를 고치는 수정 task(`origin: 사용자 …`)도 이 정의를 따른다. 옛 실행의 코드를 고치는 `change`도 이 정의로 한다.

## 먼저 읽을 것
`${CLAUDE_PLUGIN_ROOT}/references/practices/implementation-practice.md`, `${CLAUDE_PLUGIN_ROOT}/references/practices/build-and-test.md`, `${CLAUDE_PLUGIN_ROOT}/references/practices/test-rules.md`, 설계 정본의 해당 절, 흐름 규약 파일(있으면). 수정 task면 경우 파일 `references/kinds/implementation/fix.md`도.

판정자: `${CLAUDE_PLUGIN_ROOT}/references/practices/test-rules.md`

## 하는 일
1. 받은 코드 폴더에서만 일한다. 폴더 안에는 코드 변경 외의 파일을 만들지 않는다.
2. 머리 파일의 「건드릴 파일」 안에서 구현하고 테스트를 함께 쓴다. 밖의 파일을 고쳐야 하면 고친 뒤 결과에 파일과 이유를 적는다(읽기 판정이 붙는다).
3. 흐름 규약 파일의 이름·형식·오류 코드를 따른다. 새로 만든 공용 이름·형식·오류 코드와 기각한 대안은 결과의 「규약 추가」에 적는다. 다음 구현 task가 이것을 받는다.
4. 작업을 끝낼 때 빠른 피드백을 위한 **개발 검사**로 관련 테스트를 돌려 통과를 확인한다. 이 결과는 독립 판정이 아니다. 공유 자원(dev DB, 포트)을 쓰는 명령은 `recon.md`의 잠금 규칙을 따르고, 사용 중이면 건너뛰어 이상 신호에 적는다.
5. **커밋하지 않는다.** 결과에 커밋 메시지를 적는다(저장소의 스타일, AI 표시 줄 없음). 메인이 자체 검증 뒤 커밋한다.
6. 인수 기준을 닫는 테스트마다 「변이 확인 지시」(어느 줄을 어떻게 바꾸면 어느 테스트가 실패해야 하는가, 꼴은 아래 줄)를 적는다. 작성자는 잠금이 필요한 시험을 돌리지 못해 변이를 직접 확인할 수 없는 경우가 많다. 그래서 지시마다 효과 근거를 적고, 돌릴 시험의 계층과 좁힘도 아래 줄대로 적는다(낮은 계층 먼저, E2E는 배선 변이에만 좁혀서). 근거를 찾지 못한 지시는 「확인 안 된 것」에 둔다.
   - 코드 task는 인수 기준을 닫는 테스트마다 파일:줄, 어떻게 바꾸는지, 실패해야 하는 테스트, 효과 근거, 돌릴 명령을 적는다. 효과 근거는 바꾼 줄이 실제 동작을 바꾸는 근거다 — 가리키는 선택자·이름·키가 있는 파일:줄과, 그 값을 덮는 다른 규칙·정의가 없음을 찾아본 결과(CSS면 같은 요소에 걸리는 더 센 선택자를 저장소 전체에서). 실패해야 하는 테스트는 그 인수 기준을 닫는 테스트(설계 「테스트 전략」이 배정한 계층)다. 같은 줄을 더 낮은 계층의 시험도 단언하면 그 시험을 먼저 적는다. 그 인수 기준을 E2E가 닫으면 E2E는 변이가 배선(이벤트 연결, CSS 실제 숨김, 저장·전송 경로)일 때 적는다 — 배선이 아닌 변이로 지켜지는 E2E 단언은 읽기 판정의 "테스트가 Then을 직접 단언" 확인이 본다. 다만 E2E가 닫는 인수 기준마다 E2E 변이 지시를 하나 이상 둔다(그 E2E가 실제로 실패할 수 있음을 한 번은 본다). E2E를 적을 때는 실패해야 할 시험만 고르는 좁힘(`--grep "{제목}"` 또는 파일:줄)과 `--max-failures={실패해야 할 시험 수}`를 함께 적는다. 변이가 빌드 산출물에 들어가면 "빌드 필요"를 적는다.

`TODO`만 남긴 자리 표시 구현, 테스트 건너뜀 표시로 우회하는 것은 완료가 아니다. 막히면 막혔다고 결과에 쓴다.
테스트를 끄거나 기대값을 실제 결과에 맞춰 바꿔 통과시키지 않는다. 기대값이 틀렸다고 판단하면 근거와 함께 보고한다. 예외를 삼키는 `catch`도 두지 않는다.

### 결과에 반드시 적는 것
- 설계에 없던 선택(→ 「정해 주실 것」 또는 「알릴 것」)
- 설계와 달라진 점과 이유(→ 「알릴 것」). 없으면 "없음"이라고 분명히 쓴다
- 판정 위치를 옮긴 인수 기준(→ 「알릴 것」)
- 대상 밖에서 바꾼 파일과 이유. 다른 흐름이 이번 실행에서 만든 파일은 고치지 않고 `이상 신호`로 알린다(메인이 흐름 지도 기준으로 가른다)
- 돌려 볼 수 있는 task면 실행 방법과 확인할 것(→ 본문의 「직접 돌려 보기」. 승인 화면에 올리지 않는다)
- 메인이 해야 할 일(메인이 실행할 명령)과 잠금 사용 중이라 못 돌린 테스트(→ `이상 신호`와 「실행 기록」. 「하실 일」에 쓰지 않는다. 못 돌린 테스트는 실행 판정이 돌린다, 공통 계약 「실행을 흔들지 않는다」)

## 승인 화면
(구현·수정 task는 정해 주실 것·하실 일이 비면 알림으로 지나간다. 다른 흐름이 이번 실행에서 만든 파일은 고치지 않는다 — 위 「결과에 반드시 적는 것」)
- 정해 주실 것: 설계에 없던 선택 가운데 사용자가 정할 것
- 하실 일·허용 요청: 사용자만 할 수 있는 일(계정·콘솔·권한, 권한 시스템이 거부한 작업). 해도 되고 안 해도 되는 안내와 메인의 일은 넣지 않는다
- 알릴 것: 설계와 달라진 점, 판정 위치를 옮긴 인수 기준
- 확인 안 된 것: 실제 경로로 못 돌린 검사
- 건수만: 설계대로 한 작업, 통과 테스트 수, 변경 파일 수, "부분"으로 표시한 인수 기준

「알릴 것」에 달라진 점을 빠뜨리지 않는다. 요구사항을 바꾸는 달라짐은 「알릴 것」이 아니라 「정해 주실 것」이다. 알림으로 지나간 task는 흐름별 검증이 전부 다시 읽는다.

## 자체 검증 (실행 판정 + 읽기 판정: 조건)
메인이 하는 순서(1 기계 대조, 3 읽기 판정이 붙는 조건)는 `references/kinds/implementation/main-order.md`, 2 실행 판정(독립 최종 검사인 빌드·관련 테스트·변이 확인)의 절차는 `references/kinds/implementation/run-check.md`에 있다.
3. **읽기 판정**(devflow-harness:read-judge, 조건이 될 때만): 변경 전부를 읽고 머리 파일의 대상 파일·시그니처·결정 번호와 대조한다. 달라진 점이 결과에 빠짐없이 적혔는지, 테스트가 Then을 직접 단언하는지, 이번 변경이 더하거나 고친 시험이 `references/practices/test-rules.md` ②·③·④·⑤·⑥을 어기지 않는지(어기면 규칙 번호와 파일:줄로 실패) 본다. `origin`이 사용자 원문인 task(수정 task라 늘 읽기 판정을 받는다)는 그 요구가 변경에 빠짐없이, 그보다 넓지 않게 반영됐는지 본다.
4. 가정을 확인하는 task에 읽기 판정이 붙으면(3의 조건) 판정자가 가정에 적힌 대상에서 실행됐는지 본다. 아니면 "미확인 유지".
5. 인수 기준을 이 task에서 닫지 못하면 "부분(흐름별 검증에서 판정)"으로 표시하고 통과로 세지 않는다.

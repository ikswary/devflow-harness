# 마무리 task: 메인 순서

읽는 때: 메인이 마무리 task(`wrap-up`)를 다룰 때.

- 마무리 작성자를 띄우기 전에 `collect.py {실행 폴더} {이 task 폴더}`를 돌려 「확인 안 된 것」·백로그 목록을 파일로 뽑는다(`unverified-list.md`와 `backlog-list.md`가 생긴다). 작성자에게는 두 파일의 경로만 준다. 목록 본문을 메인이 손으로 모으거나 프롬프트에 옮기지 않는다. 종료 코드 3이면 「뽑지 못한 task」를 메인이 직접 확인해 파일에 덧붙인 뒤 띄운다.

뒤 절반(내보내기, 메인):
1. 실행 승인(`stage=실행승인`)을 받아 `--status 진행 stage=실행 --record "승인|…"`(꼴은 3절 「답의 처리」)로 적으면 명령이 얼려진다. 문서 변경을 커밋한다(작성자가 적은 메시지, 파일 명시). 그 깨끗한 HEAD에서 실행 판정자가 전체 검증을 새로 돌려 최종 배포 후보 CI의 commit·artifact를 기록한다. 흐름 하나여도 생략하지 않는다.
2. 병합 방식이면 실행 전에 기계로 확인한다.
   - 병합이 바꾸는 파일(`git diff --name-only {개발 기준 브랜치}...{브랜치}`)과 원래 폴더의 커밋 안 된 변경(`git status --porcelain`)이 겹치지 않는다.
   - 원래 폴더에서 다른 실행이 돌고 있지 않다(`_workspace`의 끝나지 않은 실행, `recon.md`의 잠금).
   - 원래 폴더가 개발 기준 브랜치를 꺼내 두었다.
   하나라도 걸리면 **실행하지 않고** 명령과 걸린 이유를 사용자에게 안내한다(사용자가 직접 하거나 조건이 풀린 뒤 다시. 겹침·꺼낸 브랜치는 `exec.py`도 실행 전에 본다). 사용자가 직접 넣었으면 명령을 돌리지 않고 결과승인으로 간다(`--verify`가 넣는 브랜치의 끝이 개발 기준 브랜치에 들어 있는지로 받고, 완료 때 `exported_commit`은 그 끝으로 적힌다).
3. `exec.py --step 실행승인:{n}`으로 실행한다. 원래 폴더에서 실행하는 것은 이 병합뿐이다(배포 실행의 배포 기록도 같은 방식으로 넣는다). 병합이 끝나면 스크립트가 `exported_commit`을 적는다.
4. 자체 검증(뒤 절반): `exec.py --verify` 통과(메인 실행).
5. 결과 승인(`stage=결과승인`): 실행 결과(명령, 종료 코드, 넣은 뒤 브랜치의 끝)를 보여 준다. 답을 받아 `완료 stage=끝`으로 바꾸고 실행의 끝 절차(9절)로 간다.

실패하면 `완료`로 바꾸지 않고 실패 내용을 보여 주고 묻는다. 되돌리는 명령을 스스로 실행하지 않는다.

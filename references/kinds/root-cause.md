# 원인 분석 task (`root-cause`)

버그를 재현하고 근본 원인을 증거와 함께 확정한 뒤 수정안을 낸다. 버그로 시작하는 실행의 시작 task이고, 실행 도중 원인을 모르는 실패가 나왔을 때도 만든다.

## 먼저 읽을 것
`${CLAUDE_PLUGIN_ROOT}/references/practices/root-cause-analysis.md`(절차), `${CLAUDE_PLUGIN_ROOT}/references/practices/build-and-test.md`, `${CLAUDE_PLUGIN_ROOT}/references/practices/test-rules.md`.

판정자: `${CLAUDE_PLUGIN_ROOT}/references/practices/test-rules.md`

## 하는 일
1. 증상 정리(기대 동작과 실제 동작). 기대 동작이 요청문과 질문 task의 답으로 정해지지 않으면 `writer.md` 2절대로 닫는다.
2. 재현. 가능하면 실패하는 테스트로 재현한다.
3. 가설을 하나씩 확인·기각하고 근거(파일:줄, 로그, 실행 결과)를 남긴다.
4. 근본 원인, 영향 범위(같은 패턴이 있는 다른 위치), 수정안 2개 이상과 추천.

기대 동작과 재현 테스트가 인수 기준을 대신한다.

재현할 수 없으면 재현을 지어내지 않는다. 시도한 방법과 대체 증거를 적고 「확인 안 된 것」에 올린다.

### 폴더
메인이 이 task를 시작하기 전에 코드 폴더를 만들고 기준선을 잰다. 프롬프트로 코드 폴더를 받는다. 재현 테스트는 그 폴더의 테스트 위치에 쓰고 **커밋하지 않는다**. 고른 수정안의 첫 구현 task가 자기 변경과 함께 커밋한다. 제품 코드는 고치지 않는다. 분석과 수정을 섞으면 무엇이 문제를 고쳤는지 증명하기 어렵다.

## 승인 화면
- 정해 주실 것: 수정안(안마다 무엇이 달라지는지), 고칠 범위(영향 범위 가운데 이번에 고칠 곳)
- 알릴 것: 근본 원인 한 줄, 영향 범위
- 확인 안 된 것: 재현하지 못한 경로
- 건수만: 기각한 가설 수

## 자식 목록
자식 kind: `implementation`, `flow-verify`, `wrap-up`, `design`

**수정안마다** 자식 행을 미리 적는다(범위, 판정 기준, 건드릴 파일, 고쳐졌음을 확인하는 방법). 승인에서 고른 안의 행만 메인이 구현 task로 만든다(행에 `- option: 수정안/가`처럼 안을 적는다. 여러 안에 걸치면 쉼표로. 메인이 고른 안을 `spawn_children.py --option`으로, 사용자가 나중에 하자고 한 안은 `--backlog-option`으로 넘긴다). 그리고 다음 행을 넣는다.
- 흐름별 검증 task(`kind: flow-verify`): 범위, 판정 기준(재현 테스트 통과, 영향 범위에서 고치기로 한 곳), 써 볼 방법.
- 마무리 task(`kind: wrap-up`).
설계 판단이 큰 수정이면 구현 대신 설계 task(`kind: design`)를 자식으로 둔다.
이 실행의 흐름 이름은 실행 슬러그와 같다.

## 자식 행 계약
없음

## 자체 검증 (실행 판정 + 읽기 판정)
1. 재현 테스트가 지금 코드에서 실패한다(실행 판정이 독립 실행. 재현할 수 없으면 사유와 대체 증거가 있는가).
2. 결론이 인용한 코드 위치와 로그가 실재하고 결론을 뒷받침한다(읽기 판정이 인용을 하나씩 연다. 다른 설명이 가능한지도 본다).
3. 기각한 가설마다 근거가 있다.
4. 영향 범위 검색을 판정자가 다시 실행해 같은 결과가 나온다.
5. 수정안마다 고쳐졌음을 확인하는 방법이 적혀 있다. 수정안이 시험의 판정을 느슨하게 하면(재시도, 제한 시간 늘림, 건너뜀, 허용 범위 넓힘) 그것이 가릴 수 있는 실패, 거는 원인 오류의 범위, 가려진 것을 recon 표준 명령 출력에서 볼 방법이 실제 출력 줄과 함께 적혀 있다(`references/practices/test-rules.md` ④).

# 설계 task (`design`)

묶음의 요구사항을 기존 코드 구조에 맞는 변경 계획으로 바꾸고, 구현과 검증 task의 행을 만든다. 코드는 쓰지 않는다(짧은 시그니처와 예시만).

## 먼저 읽을 것
`${CLAUDE_PLUGIN_ROOT}/references/practices/design-doc.md`(설계서를 쓰는 기준), `${CLAUDE_PLUGIN_ROOT}/references/practices/test-rules.md`, 정본 `spec\{묶음}.md`, 의존하는 설계의 정본, 기획 정본 `spec\brief.md`(「정책」·「화면 흐름」, 있으면), 그 묶음의 화면 정본 `ui\{묶음}.md`(「시안」의 채택 줄 포함)와 UI 규약 `ui\rules.md`(있으면. 화면 정본이 있으면 경우 파일 `references/kinds/design/ui-spec.md`도). 요구사항 없이 시작한 설계(동작을 바꾸지 않는 변경)는 정본 대신 질문 task의 답과 머리 파일 「범위」의 이어받는 task를 읽고, 인수 기준 대신 "유지할 동작 목록과 지키는 테스트"(없으면 고정 테스트를 쓰는 구현 task가 첫 행)와 이 설계가 새로 정하는 관찰 가능한 기준을 정본에 쓴다.

판정자: `${CLAUDE_PLUGIN_ROOT}/references/practices/test-rules.md`

## 하는 일
1. **결정 지도를 먼저 쓴다.** 결정 목록, 결정 사이의 의존, 사용자 결정 표시. 답이 없는 사용자 결정에 나머지가 의존하면 `writer.md` 2절대로 거기서 닫는다. 결정이 많으면 결정 사슬을 따라 스스로 줄인다(예: 저장소 선택 → 격리 → 접근 방식).
2. 정본 `design\{흐름}.md`를 쓴다: 변경 개요, 결정 기록(선택지·선택·이유·종류), 구성 요소·인터페이스·데이터 변경, 테스트 전략, **인수 기준마다 닫는 task와 관찰 방법**, 확인 안 된 가정마다 확인 대상(로컬/dev/배포된 것)과 확인할 task.
3. 결정마다 종류를 붙인다.
   - **사용자 결정**: 선택지에 따라 돈, 사용자가 할 일, 범위, 고객·운영자가 겪는 것이 달라지고, 요구사항과 이전 답으로 하나로 정해지지 않는다.
   - **알릴 결정**: 아래 질문에 하나라도 "예". 걸린 번호를 적는다.
     1. 바꾸려면 저장된 데이터나 만들어진 자원을 옮기거나 다시 만들어야 하는가.
     2. 저장소 밖에서 보이는가(주소, API 경로, 고객이나 운영자가 읽는 문구). 명령을 돌리는 사람의 화면에 새로 나오는 줄, 실패·경고 문구, 사용법·도움말 문구도 운영자가 읽는 문구다.
     3. 외부 서비스·계정·요금제를 새로 쓰거나 설정을 바꾸는가.
     4. 승인된 요구사항이나 이전 결정의 문구를 고쳐야 성립하는가(요구사항에 없던 것을 더하거나 빼면 알리는 것이 아니라 묻는다).
     5. 개인정보·비밀값·접근 권한이 놓이는 곳이나 범위를 바꾸는가.
     6. 사용자의 말을 해석해 적용 범위를 정했는가.
   - **관례 결정**: 따른 기존 코드의 위치(파일:줄), 또는 다른 선택지가 어기는 인수 기준 번호를 댈 수 있을 때만. 못 대면 관례가 아니다.
4. "배포된 것"으로 확인할 가정은 확인 동작을 읽기와 쓰기로 나눠 적는다. 쓰기가 있는 경로를 읽기만으로 확인하게 두지 않는다.

**실행 전체 몫**(경우 파일 `references/kinds/design/run-wide.md`의 목록과 자식 목록의 전체 검증·마무리·배포 계획 행)은 그 실행에서 가장 먼저 끝나는 설계 task가 쓴다: 공통 설계가 있으면 공통 설계, 설계가 하나면 그 설계. 공통 설계 없이 설계가 둘 이상 나란히 돌면 어느 설계도 실행 전체 몫을 쓰지 않고, 메인이 설계 task 행이 모두 생긴 뒤 **실행 전체 설계 task**(`kind: design`, 제목 `설계 — 실행 전체`, 흐름 없음, `depends_on`에 모든 설계 task, 판정 기준은 「자체 검증」 가운데 실행 전체 몫에 해당하는 것)를 만들어 이 몫만 맡긴다. 먼저 끝난 설계에 맡기지 않는 것은, 그때는 다른 설계가 건드릴 파일을 몰라 흐름 사이 겹침을 다 적을 수 없기 때문이다. 나란히 도는 설계는 찾은 겹침을 지금처럼 자기 정본에 적고(자체 검증 6), 실행 전체 설계가 그것을 모아 흐름 지도 전체를 쓴다.

흐름 사이 겹침의 경우(흐름 지도가 겹침마다 이 가운데 하나와 이유를 적는다):
- **각자 진행**: 실행 시작 때 이미 있던 파일에 두 흐름이 서로 다른 이름의 항목만 더하고, 순서가 동작을 바꾸지 않는다(설정, 등록, 내보내기 목록). 흐름을 합치지 않고 각자 고친다. 합칠 때 충돌은 받아오기에서 맞춘다.
- **이어 붙이기**: 한 흐름이 다른 흐름이 이번 실행에서 만든 코드를 쓰거나 고친다. 쓰는 흐름은 만드는 흐름의 의존한 구현 task가 커밋되면 그 커밋에서 갈라져 바로 시작한다. 만드는 흐름의 검증·합치기를 기다리지 않는다. 흐름 지도에 "쓰는 흐름 ← 만드는 흐름 @ 의존한 task"를 적는다.
- **그 밖의 겹침**(같은 줄을 둘 다 고침, 등록 순서가 동작을 바꿈, DB 마이그레이션을 함께 바꿈, 셋 이상이 얽힘 등): 아직 겪지 않은 경우라 규칙을 정하지 않았다. 「정해 주실 것」으로 올린다. 답은 이 정의에 규칙으로 더한다.

그 뒤의 설계 task는 흐름 지도의 겹침 분류를 따르고, 흐름 지도에 없던 겹침을 찾으면 「알릴 것」에 경우와 함께 올린다(그 밖의 겹침이면 「정해 주실 것」). 결과에 「전체 검증에 더할 것」(관점, 실제 경로 확인 대상, 어느 기능에도 넣지 못한 인수 기준)을 본문에 쓰고 「알릴 것」에 한 줄로 올린다.

## 승인 화면
- 정해 주실 것: 답 없는 사용자 결정, 요구사항을 바꾸는 제안, 실행 시작 때의 커밋 안 된 변경과 겹치는 파일
- 하실 일·허용 요청: 계정·콘솔·결제·권한
- 알릴 것: 알릴 결정(한 줄씩 + 걸린 질문 번호), 전체 검증에 더할 것
- 답하신 것의 반영: 답을 어떤 범위로 적용했는지, 그 답으로 뒤집힌 이전 결정
- 확인 안 된 것: 확인 안 된 가정과 받아들인 위험(틀리면 바뀌는 결정, 확인할 task). 틀려도 위 칸이 안 바뀌는 가정은 「건수만」으로
- 건수만: 관례 결정 수와 정본의 위치

## 자식 목록
자식 kind: `implementation`, `flow-verify`, `full-verify`, `wrap-up`, `deploy-plan`

- 구현 task 행(`kind: implementation`): 범위, 판정 기준(이 task에서 닫는 단언), 건드릴 파일(**테스트 파일도 적는다.** 여기에 없는 파일을 바꾸면 기계 조건에 걸려 읽기 판정이 붙는다. 새로 만들 파일은 `tests/unit/example*.test.ts`처럼 패턴으로 적는다), 시그니처와 결정 번호(새로 내보내는 이름과 시그니처, 따르는 결정 번호), 난이도, 닫는 인수 기준. `단순`은 판단 없이 패턴을 따라 쓰는 작업에만 붙인다.
- 그 흐름의 흐름별 검증 task 행(`kind: flow-verify`): 범위(그 흐름이 닫는 인수 기준 전부), 판정 기준, 사람이 직접 써 볼 방법. 시작 조건은 `board.py`가 보므로 구현 task에 의존하지 않아도 된다.
- 한 흐름의 구현 task는 적은 순서대로 차례로 진행한다. 다른 흐름의 task에는 의존하지 않는다. 예외는 이어 붙이는 흐름의 첫 코드 task 하나로, 만드는 흐름의 task id가 이미 있을 때만 그 의존한 task에 `depends_on`으로 의존한다(갈라질 커밋이 생겨야 시작할 수 있고, 그 task가 멈추면 함께 멈춘다). 공통 설계 없이 나란히 도는 설계는 아직 id가 없으니 적지 않는다(흐름 지도는 실행 전체 설계가 쓰고, 메인이 받아오기로 맞춘다). 쓰는 흐름의 첫 구현 task 행에 "갈라질 커밋: {만드는 흐름}의 {task id} 커밋"을 범위에 적는다.

## 자체 검증 (읽기 판정)
스스로 줄인 task에는 닫은 범위에 해당하는 기준만 적용한다.
1. 맡은 인수 기준마다 닫는 task와 관찰 방법이 있고, 그 task의 판정자가 그 task를 판정하는 때에 그 관찰을 할 수 있다(공통 계약 「판정 기준은 확인할 수 있어야 한다」·「판정 시점의 사실」). 앞 단계가 관찰을 막으면 실패다.
2. 설계가 인용한 기존 코드 위치가 실재하고 내용이 인용한 대로다(판정자가 인용을 연다).
3. 관례로 분류된 결정 **전부**에 확인 질문 1~6을 다시 적용한다. 하나라도 걸리면 분류가 틀렸다(`judge.md` 「칸 분류 확인」에 적는다). 고칠 것이 관례에서 알릴 결정으로 칸을 옮기는 것뿐이면 「칸 분류 확인」에만 적고 실패로 세지 않는다(`screen.py`가 옮겨 보인다. 작성자를 다시 부를 일이 아니다). 사용자 결정이어야 하면(질문 4의 괄호, 요구사항에 있는 것을 빼거나 없던 것을 더함) 실패다.
4. 가정마다 확인 대상과 확인 task가 있다. "배포된 것"으로 확인할 가정에 읽기와 쓰기가 나뉘어 있다. 쓰기가 있는 경로를 읽기만으로 확인하면 실패.
5. 답이 없는 사용자 결정에 의존하는 결정이나 자식 행이 결과에 없다. 있으면 실패(작성자가 그 지점에서 닫아야 했다).
6. 자식 목록: 인수 기준이 빠짐없이 한 task에 맡겨졌다 / 건드릴 파일이 겹치는 task 사이에 순서가 있다 / 판정 기준이 공통 계약 「판정 기준은 확인할 수 있어야 한다」대로 확인할 수 있고, 명령 실행 기준은 기준선 대비로 쓰였다(`writer.md` 5절) / 다른 흐름과 건드릴 파일이 겹치는 곳마다 흐름 지도에 경우(각자 진행 / 이어 붙이기 / 그 밖)와 이유가 있다. "각자 진행"은 세 조건(시작 때 있던 파일, 서로 다른 이름의 항목만 더함, 순서 무관)을 모두 채운다(판정자가 파일의 기준 커밋 존재와 변경 모양을 확인한다). 다른 흐름이 이번 실행에서 만드는 파일을 쓰거나 고치면 "이어 붙이기"다.
7. 「테스트 전략」의 인수 기준마다 계층과 그 계층을 고른 이유가 있다. 같은 단언을 두 계층에 두면 이유가 있고, "모든 X에서" 같은 인수 기준을 계층의 합으로 지키면 그것이 「정해 주실 것」(또는 답한 결정 번호)으로 올라가 있다(`references/practices/test-rules.md` ①).

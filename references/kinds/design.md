# 설계 task (`design`)

묶음의 요구사항을 기존 코드 구조에 맞는 변경 계획으로 바꾸고, 구현과 검증 task의 행을 만든다. 코드는 쓰지 않는다(짧은 시그니처와 예시만).

## 먼저 읽을 것
`${CLAUDE_PLUGIN_ROOT}/references/practices/design-doc.md`(설계서를 쓰는 기준), `${CLAUDE_PLUGIN_ROOT}/references/practices/test-rules.md`, 정본 `spec\{묶음}.md`, 의존하는 설계의 정본, 기획 정본 `spec\brief.md`(「정책」·「화면 흐름」, 있으면), 그 묶음의 화면 정본 `ui\{묶음}.md`(「시안」의 채택 줄 포함)와 UI 규약 `ui\rules.md`(있으면. 화면 정본이 있으면 경우 파일 `references/kinds/design/ui-spec.md`도). 요구사항 없이 시작한 설계(동작을 바꾸지 않는 변경)는 정본 대신 질문 task의 답과 머리 파일 「범위」의 이어받는 task를 읽고, 인수 기준 대신 "유지할 동작 목록과 지키는 테스트"(없으면 고정 테스트를 쓰는 구현 task가 첫 행)와 이 설계가 새로 정하는 관찰 가능한 기준을 정본에 쓴다.

판정자: `${CLAUDE_PLUGIN_ROOT}/references/practices/test-rules.md`

## 하는 일
1. **결정 지도를 먼저 쓴다.** 결정 목록, 결정 사이의 의존, 사용자 결정 표시. 답이 없는 사용자 결정에 나머지가 의존하면 `writer.md` 2절대로 거기서 닫는다. 결정이 많으면 결정 사슬을 따라 스스로 줄인다(예: 저장소 선택 → 격리 → 접근 방식).
2. 정본 `design\{흐름}.md`를 쓴다: 변경 개요, 결정 기록(선택지·선택·이유·종류), 구성 요소·인터페이스·데이터 변경, 시험 표, **인수 기준마다 닫는 task와 관찰 방법**, 확인 안 된 가정마다 확인 대상(로컬/dev/배포된 것)과 확인할 task. 기획 「앞으로의 계획」이 있으면 대비 범위의 근거로 인용한다.
   - **로컬은 설계가 닫는다**: 파일(저장소, 기준본 같은 로컬 사본)을 읽어 답이 나오는 가정은 직접 읽어 닫고 넘기지 않는다. 넘길 수 있는 것은 dev·배포 환경이나 실행(빌드, 앱 띄우기, 시험)이 필요한 가정뿐이다. 읽어 보니 요구사항과 어긋나면 확인 안 된 것이 아니라 요구사항을 바꾸는 제안이다(「정해 주실 것」).
3. 결정마다 종류를 붙인다(`references/roles/writer.md` 2절).
4. "배포된 것"으로 확인할 가정은 확인 동작을 읽기와 쓰기로 나눠 적는다. 쓰기가 있는 경로를 읽기만으로 확인하게 두지 않는다.

**실행 전체 몫**(경우 파일 `references/kinds/design/run-wide.md`의 목록과 자식 목록의 전체 검증·마무리·배포 계획 행)은 설계가 하나면 그 설계가 쓴다. 설계가 둘 이상이면 공통 설계가 있어도 어느 설계도 실행 전체 몫을 쓰지 않는다. 메인이 만드는 **실행 전체 설계 task**(`kind: design`, 머리 키 `run_wide: true`)가 이 몫만 맡는다. 프롬프트에 `실행 전체 몫 쓰지 않음`이 있으면 전체 검증·마무리·배포 계획 행을 쓰지 않는다(판정자도 그 행이 없음을 본다). 공용 형식·오류 코드·상수 위치는 뒤 설계가 읽어야 하므로 공통 설계의 정본에 쓴다. 각 설계는 찾은 겹침을 자기 정본에 적고(자체 검증 6), 실행 전체 설계가 그것을 모아 흐름 지도 전체를 쓴다.

흐름 사이 겹침의 경우는 같은 경우 파일(`design/run-wide.md`)에 있다.

찾은 겹침은 「알릴 것」에 경우와 함께 올린다(그 밖의 겹침이면 「정해 주실 것」). 결과에 「전체 검증에 더할 것」(관점, 실제 경로 확인 대상, 어느 기능에도 넣지 못한 인수 기준)을 본문에 쓰고 「알릴 것」에 한 줄로 올린다.

## 승인 화면
- 정해 주실 것: 답 없는 사용자 결정, 요구사항을 바꾸는 제안, 실행 시작 때의 커밋 안 된 변경과 겹치는 파일
- 하실 일·허용 요청: 계정·콘솔·결제·권한
- 알릴 것: 알릴 결정(한 줄씩 + 걸린 질문 번호), 전체 검증에 더할 것
- 답하신 것의 반영: 답을 어떤 범위로 적용했는지, 그 답으로 뒤집힌 이전 결정
- 확인 안 된 것: 확인 안 된 가정과 받아들인 위험(틀리면 바뀌는 결정, 확인할 task). 틀려도 위 칸이 안 바뀌는 가정은 「건수만」으로
- 건수만: 관례 결정 수와 정본의 위치

화면 차례, 제안 도면, `### 리뷰 자료`에 쓸 것은 경우 파일 `references/kinds/design/screen.md`. 작성자가 먼저 읽는다.

## 자식 목록
자식 kind: `implementation`, `fe-implementation`, `be-implementation`, `probe`, `flow-verify`, `full-verify`, `wrap-up`, `deploy-plan`

코드 행의 kind 가름, `[탐침]` 가정의 탐침 행, 인프라 결정 판정은 경우 파일 `references/kinds/design/rows.md`.
- 구현 task 행(`kind: implementation`): 범위, 판정 기준(이 task에서 닫는 단언), 건드릴 파일(**테스트 파일도 적는다.** 여기에 없는 파일을 바꾸면 기계 조건에 걸려 읽기 판정이 붙는다. 새로 만들 파일은 `tests/unit/example*.test.ts`처럼 패턴으로 적는다), 시그니처와 결정 번호(새로 내보내는 이름과 시그니처, 따르는 결정 번호), 난이도, 닫는 인수 기준. `단순`은 판단 없이 패턴을 따라 쓰는 작업에만 붙인다.
- 그 흐름의 흐름별 검증 task 행(`kind: flow-verify`): 범위(그 흐름이 닫는 인수 기준 전부), 판정 기준, 사람이 직접 써 볼 방법. 시작 조건은 `board.py`가 보므로 구현 task에 의존하지 않아도 된다.
- 한 흐름의 구현 task는 적은 순서대로 차례로 진행한다. 다른 흐름의 task에는 의존하지 않는다. 예외는 이어 붙이는 흐름의 첫 코드 task 하나로, 만드는 흐름의 task id가 이미 있을 때만 그 의존한 task에 `depends_on`으로 의존한다(갈라질 커밋이 생겨야 시작할 수 있고, 그 task가 멈추면 함께 멈춘다). 아직 id가 없으면 적지 않는다(설계가 둘 이상이면 구현은 실행 전체 설계가 끝난 뒤 시작하고, 갈라질 자리는 흐름 지도가 정한다). 쓰는 흐름의 첫 구현 task 행에 "갈라질 커밋: {만드는 흐름}의 {task id} 커밋"을 범위에 적는다.

## 자체 검증 (읽기 판정)
스스로 줄인 task에는 닫은 범위에 해당하는 기준만 적용한다.
1. 맡은 인수 기준마다 닫는 task와 관찰 방법이 있고, 그 task의 판정자가 그 task를 판정하는 때에 그 관찰을 할 수 있다(공통 계약 「판정 기준은 확인할 수 있어야 한다」·「판정 시점의 사실」). 앞 단계가 관찰을 막으면 실패다.
2. 설계가 인용한 기존 코드 위치가 실재하고 내용이 인용한 대로다(판정자가 인용을 연다).
3. 관례로 분류된 결정 **전부**에 확인 질문 1~6을 다시 적용한다. 하나라도 걸리면 분류가 틀렸다(`judge.md` 「칸 분류 확인」에 적는다). 고칠 것이 관례에서 알릴 결정으로 칸을 옮기는 것뿐이면 「칸 분류 확인」에만 적고 실패로 세지 않는다(`screen.py`가 옮겨 보인다. 작성자를 다시 부를 일이 아니다). 사용자 결정이어야 하면(질문 4의 괄호, 요구사항에 있는 것을 빼거나 없던 것을 더함) 실패다.
4. 가정마다 확인 대상과 확인 task가 있다. 파일을 읽어 닫을 수 있는 가정이 남아 있으면 실패(실행이나 dev·배포가 필요한 가정은 넘겨도 된다). "배포된 것"으로 확인할 가정에 읽기와 쓰기가 나뉘어 있다. 쓰기가 있는 경로를 읽기만으로 확인하면 실패.
5. 답이 없는 사용자 결정에 의존하는 결정이나 자식 행이 결과에 없다. 있으면 실패(작성자가 그 지점에서 닫아야 했다).
6. 자식 목록: 인수 기준이 빠짐없이 한 task에 맡겨졌다 / 건드릴 파일이 겹치는 task 사이에 순서가 있다 / 판정 기준이 공통 계약 「판정 기준은 확인할 수 있어야 한다」대로 확인할 수 있고, 명령 실행 기준은 기준선 대비로 쓰였다(`writer.md` 5절) / 다른 흐름과 건드릴 파일이 겹치는 곳마다 흐름 지도에 경우(각자 진행 / 이어 붙이기 / 서로 다른 줄 고침 / 모아 붙이기 / 그 밖)와 이유가 있다. "각자 진행"은 세 조건(시작 때 있던 파일, 서로 다른 이름의 항목만 더함, 순서 무관)을 모두 채운다(판정자가 파일의 기준 커밋 존재와 변경 모양을 확인한다). 다른 흐름이 이번 실행에서 만드는 파일을 쓰거나 고치면 "이어 붙이기"다.
7. 「시험 표」의 인수 기준마다 계층과 그 계층을 고른 이유가 있다. 같은 단언을 두 계층에 두면 이유가 있고, "모든 X에서" 같은 인수 기준을 계층의 합으로 지키면 그것이 「정해 주실 것」(또는 답한 결정 번호)으로 올라가 있다(`references/practices/test-rules.md` ①). 1.2.0부터 시작한 task는 시험 표의 칸이 닫힌 값이고, 닫는 인수 기준마다 시험이 하나 이상이거나 예외 행이 있다.
8. 경우 파일 `references/kinds/design/checks.md`의 8~11과 `references/kinds/design/screen.md`의 12~14.

# 변경 task (`change`)

승인된 산출물을 고친다. 원래 task는 닫힌 채 두고, 바뀐 부분만 다룬다. 행(범위, 판정 기준)은 부모가 없으므로 메인이 쓴다.

생기는 경우: 승인에서 산출물을 바꾸는 답이 옴(준비된 선택지를 고른 것은 제외) / 뒤 task가 승인된 요구사항·설계를 고쳐야 함 / 사용자가 `나눠서 다시`를 고름.

코드를 고치는 변경은 `kind: fix`로 만든다(구현 정의를 따른다. 메인의 `task_set.py new --from-answer`가 「건드릴 파일」로 정한다). 이 정의는 정본(요구사항, 기획, 화면, 설계)을 고치는 변경에만 쓴다. 화면 정본을 고치면 설계서(`ui\{묶음}.md`)와 와이어프레임(`ui\wireframes\{묶음}.html`)을 함께 `revised\ui\…`에 둔다(와이어프레임은 그대로 복사되고 변경 이력 절이 붙지 않는다).

## 먼저 읽을 것
고칠 산출물의 블록에 해당하는 대상 kind 모듈(요구사항 개요면 `req-overview`, 상세면 `req-detail`, 기획이면 `brief`, 화면 정본이면 `ui-design`, 설계면 `design`의 모듈. 등록표 `references/registry/edges.md`의 `CHANGE_TARGETS`), 머리 파일의 `origin`이 가리키는 계기(사용자 원문 또는 지적).
- 설계 작성자(`design-writer`): 대상이 설계면 `${CLAUDE_PLUGIN_ROOT}/references/practices/design-doc.md`, 화면 정본이면 `${CLAUDE_PLUGIN_ROOT}/references/practices/ui-spec.md`, 그리고 `${CLAUDE_PLUGIN_ROOT}/references/practices/test-rules.md`
- 요구사항 작성자(`requirements-writer`): 없음

## 하는 일
1. 계기를 읽는다. 사용자의 말을 넓히거나 좁혀 해석했으면 그 해석을 「답하신 것의 반영」에 적는다.
2. **정본을 직접 고치지 않는다.** 자기 task 폴더의 `revised\`에 정본과 같은 상대 경로로 고친 판을 통째로 쓴다(예: `revised\spec\contact-form.md`). 판정과 승인을 통과하면 메인이 스크립트로 정본에 옮긴다. 「건드릴 파일」은 한 줄에 `- 경로` 하나다(설명은 괄호나 ` — ` 뒤에. 정본 밖 경로가 있거나 이 꼴이 아니면 `change`로 만들어지지 않는다). 변경이 도는 동안 다른 task가 판정받지 않은 내용을 읽지 않게 하기 위해서다.
3. 고친 곳마다 정본의 어느 절·어느 번호인지 본문에 표로 적는다(바꾸기 전 → 바꾼 뒤).
4. 영향받는 task 목록을 본문에 적는다: 이 변경으로 범위나 판정 기준이 달라지는 task(부모·자식·인수 기준 연결을 따라). 메인이 준 후보가 있으면 그것을 하나씩 확인한다. 후보마다 "바뀜(무엇이)" 또는 "그대로(이유)"를 적는다. 메인은 "그대로"인 시작 전 task의 의존을 이 task의 자체 검증 통과 뒤 푼다. 이 변경이 고친 판 밖으로 넘기는 것(형제에게 넘길 이상 신호)이 있는 task는 "바뀜"이다.

## 승인 화면
- 답하신 것의 반영: 사용자의 답(원문) → 산출물의 어디가 어떻게 바뀌었는지, 그 답으로 뒤집힌 이전 결정
- 알릴 것: 영향받는 task("바뀜/그대로"와 무엇이 어떻게 달라지는지 한 줄씩), 바뀐 자식 행
- 정해 주실 것: 답을 반영하다가 새로 생긴 결정
- 나머지 칸: 해당 블록의 task 정의를 따른다

변경 task는 계기가 사용자 답이 아니고(`origin`이 `사용자`로 시작하지 않음), `screen.py`가 "알림 조건: 충족"(정해 주실 것·하실 일이 비고 통과 못 한 기준·판정불가·판정 미완료·자원 대기 없음)이면 알림으로 지나간다. [RP-11]

## 자식 목록
자식 kind: 없음

- 변경 task는 원래 task의 자식 행이 바뀌면 「자식 목록」에 바뀐 행만 다시 쓰고, 제목과 `flow`를 원래 행과 같게 둔다(`spawn_children.py --replace`가 이 둘로 기존 task와 짝짓는다).

## 자식 행 계약
없음

## 자체 검증 (읽기 판정)
1. 계기(사용자 원문 또는 지적)가 고친 판에 그대로 반영됐다. 더 넓게도 더 좁게도 반영되지 않았다.
2. 고친 판과 지금 정본의 차이가 본문의 표와 일치한다(판정자가 두 파일을 비교한다. 표에 없는 변경이 있으면 실패).
3. 그 블록의 task 정의의 자체 검증 기준 가운데 바뀐 절에 해당하는 것.
4. 영향받는 task 목록이 있고 후보마다 "바뀜/그대로"가 있다. "그대로"인데 고친 판이 그 task가 읽는 절·결정 번호를 바꿨으면 실패. 판정자가 바뀐 인수 기준·결정 번호를 가리키는 task를 `tasks\*\task.md`에서 검색해 빠진 것이 없는지 본다(판정자는 이 확인을 위해 다른 task의 머리 파일을 읽을 수 있다).

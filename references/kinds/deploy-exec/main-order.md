# 배포 실행 task: 메인 순서

읽는 때: 메인이 배포 실행 task(`deploy-exec`)를 다룰 때.

- 사용자 할 일 대기(3절)의 (다)로 적힌 배포 실행 task는 사용자가 했다고 답해 지워진 뒤에 시작하므로, 사전 조건 단계(아래 순서 1)가 묻는 「하실 일」의 답은 그 task의 「승인 기록」에 이미 있다.
- 시작 조건: 부모 배포 계획이 `완료`. 뒤 환경(운영)이면 `depends_on`의 앞 환경 배포 실행이 `완료`이고 그 머리 파일이 `deploy_outcome: 유지`(`references/kinds/deploy-plan/multi-env.md`). 앞 환경이 `되돌림`·`보류`로 끝나면 메인이 같은 단계에서 이 task를 `보류`로 바꾸고 이유를 적는다(`board.py --ready`는 상태만 보므로).

순서(6 배포 기록은 `references/kinds/deploy-exec.md` 「하는 일」):
1. **사전 조건**: 계획의 확인 명령을 돌린다. 배포 폴더의 `HEAD`가 계획의 커밋 해시 자체이고 `git status --porcelain`이 비어 있는지, 최종 배포 후보 CI의 검증 commit·artifact가 실제 배포할 commit·artifact와 같은지도 본다. 부분 검사 기록으로 대신하지 않는다. 뒤 환경이면 앞 환경 실행 머리 파일의 `deploy_outcome`·`deployed_commit`을 대조한다. 계획의 「하실 일」을 사용자가 했는지 답이 없으면 묻는다. 하나라도 기대와 다르면 배포 명령을 실행하지 않고 보여 주고 묻는다.
2. **실행 직전 확인(운영만)**: 사전 조건이 통과한 뒤에 한 번 묻는다. 보여 줄 것: 환경 이름("운영(…)에 배포합니다"), 올릴 커밋, 계획 승인 시각, 앞 환경 결과 한 줄(유지·확인 통과 수·사람 확인 답), 사전 조건 결과. 계획 승인 뒤에 바뀐 것(배포 메모·`decisions.md`의 새 줄, 하네스 판본)이 있으면 함께 적는다. dev는 부모 승인으로 충분하다.
3. **명령**: 계획의 순서대로 `exec.py --step 실행승인:{n}`으로 하나씩 실행한다(`exec.md`·`external_progress`·로그는 스크립트가 쓴다). 로그에 남은 계정 식별자·호스트명·IP는 보여 주기 전에 가린다.
   - `[사용자 실행]` 명령과 권한 시스템에 거부된 명령: 메인이 명령을 그대로 보여 주고 사용자가 실행한다. 사용자가 알려 준 종료 결과와 출력 줄을 `exec.py --user-result 실행승인:{n} "…"`로 적는다(가린 뒤). 알려 주지 않은 값은 자체 검증에서 판정불가다.
   - 목록에 없는 명령이 필요해지거나 명령이 실패하면 다음 명령으로 가지 않고 멈춘다. 되돌리는 명령을 스스로 실행하지 않는다. 배포 도구가 스스로 되돌렸으면(계획 5의 종료 코드) 그 사실을 `exec.md`에 적는다. 그대로 5(결과 승인)로 가서 실패 내용과 계획의 되돌리기를 보여 준다.
4. **확인**: 배포 명령이 끝났으면 `devflow-harness:run-judge`를 `xjudge-{id}`로 띄워(`running_agent`에 적고, 띄우기 전에 `task_set.py {실행 폴더} {id} --judge-start xjudge-{id}`) 계획의 배포 뒤 확인 가운데 실행 판정이 돌릴 것을 돌린다. 운영에는 쓰기 확인이 없다. 공유 자원이면 실행 판정자가 명령 단위로 잠금을 잡고, 사용 중이면 실패·판정불가가 아닌 자원 대기로 반환한다. 배포 도구가 버전을 여럿 만들면 결과 줄에 마지막으로 전환된 버전을 적는다. [RP-18] 판정자가 `judge-run.md`에 확인마다 한 줄(시각, 작업 폴더, 명령, 종료 코드, 로그)을 쓴다(메인이 `exec.md`로 옮기지 않는다). **재개 때 `stage: 확인`이면 쓰기 확인을 다시 돌리기 전에 묻는다**(이미 돈 쓰기 확인이 메일·데이터를 한 번 더 만든다. `judge-run.md`와 `logs\`로 돈 것을 먼저 본다).
5. **결과 승인**(`stage=결과승인`): 화면의 재료는 `exec.md`(명령·종료 코드)와 `judge-run.md`(확인마다 결과)를 그대로 옮긴 것이다(메인의 기계 대조. 해석해 줄이지 않는다. 이 화면에는 `screen.py`를 쓰지 않는다. `result.md`가 아직 없다). 선택지: 유지 / 되돌림(계획의 되돌리기 명령을 그대로 보여 줌, 고르면 `exec.py --step 되돌림:{n}`) / 보류. 확인이 실패해도 되돌리기를 권하지 않고 묻는다. 답에 따라 `deploy_outcome`, `deployed_commit`을 적는다. 사람이 볼 확인(메일함, 화면)은 「하실 일」로 올리고 답을 승인 기록에 적는다(뒤 환경의 사전 조건이 본다). 사용자가 확인을 맡기면 `references/kinds/deploy-exec.md` 「사람 확인의 위임」.
   - 되돌림·보류면 배포 기록 문서는 쓰지 않는다. 뒤 환경의 배포 계획·실행을 같은 단계에서 `보류`로 바꾼다. 계획의 `[유지 뒤]` 명령도 실행하지 않는다.
   - **운영 브랜치 옮기기**(계획에 `[유지 뒤]` 명령이 있고 답이 `유지`일 때): `stage: 브랜치`로 `[유지 뒤]` 줄을 `exec.py --step`으로 실행한다. 실행 직전 원래 폴더의 운영 브랜치 해시가 계획의 O인지 본다(아니면 실행하지 않고 묻는다). `update-ref`가 실패하면 push하지 않고 멈춰 묻는다. 결과 승인과 따로 묻지 않는다(계획 승인과 `유지`가 승인이다).
7. **문서 넣기 승인**(`stage=넣기승인`). 묻기 전의 차례(`stage: 기록` 동안):
   1. 배포 기록 작성(6)과 읽기 판정(`rjudge-{id}`)이 커밋 전 작업 트리를 본다.
   2. 메인이 배포 폴더에서 작성자가 적은 메시지로 고친 문서 파일을 명시해 커밋한다(배포 기록 커밋). 직후 `git status --porcelain`이 비었는지 보고 `task_set.py {실행 폴더} {id} external_progress="배포 기록 커밋 {sha}"`(재개 표지).
   3. 이 커밋은 CI를 거치지 않으므로 `recon.md`에 「문서를 읽는 검사」가 있으면 그 커밋에서 그 명령을 돌려 `main-run.md`에 `## 넣기 전 문서 검사`(`- 검증 commit: {sha}`, `- 명령:`, `- 종료 코드:`, `- 로그:`)로 적는다(메인 실행. 1.1.1부터 가드가 검증 commit·종료 코드를 본다).
   4. `--status 승인대기 stage=넣기승인 external_progress=`로 묻는다.

   재개: `stage: 기록`이고 `external_progress`가 `배포 기록 커밋 {sha}`면 배포 폴더 HEAD가 그 sha인지 보고, `main-run.md`의 검증 commit이 그 sha면 4부터, 아니면 3부터 잇는다.

   화면: 문서 변경 요약(파일, 절, 적은 값), 배포 기록 커밋 SHA와 문서 검사 결과(종료 코드가 0이 아니면 맨 위에), 넣는 명령(그대로, 「정해 주실 것」의 `cmd` 울타리. 병합 줄만이고 `git add`·`git commit` 줄은 `exec.py`가 거부한다. "이 명령을 원래 폴더에서 실행합니다"). 선택지: 넣음 / 넣지 않음 / 보류(문서 검사가 실패했으면 넣음 대신 고침 / 위험 수용. 위험 수용 답은 `--record "승인|위험 수용|{원문}"`이고, 이 답이 없으면 넣는 명령을 얼리지 않는다). 넣음이면 `--status 진행 stage=넣기 --record "승인|…"`(꼴은 3절 「답의 처리」. 이때 넣는 명령과 넣는 끝(배포 기록 커밋)이 얼려진다), 넣지 않음이면 곧바로 `--status 완료 stage=끝 --record …`. 넣지 않으면 배포 기록 커밋은 배포 폴더 브랜치에만 남고 개발 기준 브랜치에는 없다. 「하실 일」로 알린다: 그 브랜치를 지우면(정리 목록) 기록이 사라지고, 다음 배포는 배포 폴더 `HEAD`가 올릴 커밋과 달라 사전 조건에서 걸린다. 되돌리거나 지우는 명령은 사용자가 고를 때만 메인이 보여 주고 실행한다.
8. **넣기**: 마무리 내보내기 5~7(병합 방식)과 같이 `exec.py --step 넣기승인:{n}`으로 한다(병합 전 기계 확인은 걸리면 실행하지 않고 명령과 이유를 안내. 배포 폴더 브랜치의 끝이 얼린 끝과 다르면 `exec.py`가 거부한다). 실패하면 `끝`으로 바꾸지 않고 실패 내용을 보여 주고 묻는다. 되돌리는 명령을 스스로 실행하지 않는다.

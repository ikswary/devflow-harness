# 화면 설계 task (`ui-design`)

화면이 있는 묶음에서 요구사항 상세 뒤(기획이 행을 쓰고 그 묶음의 상세와 UI 규약 task에 의존), 소프트웨어 설계 앞에 온다. 기획이 정한 화면 id와 흐름, 상세의 FR·AC를 받아 화면마다 요소·위계·배치·상태·조작·문구를 정본으로 쓰고 와이어프레임을 그린다. 구성 요소·데이터·코드 구조는 소프트웨어 설계의 일이라 정하지 않는다. 그 묶음의 설계 task는 상세가 이미 만들었고 이 task에 의존한다. 같은 종류의 특별한 task로 **UI 규약 task**(제목 `화면 설계 — UI 규약`, `ui\rules.md`를 씀)가 있다(그 task의 자체 검증은 경우 파일 `references/kinds/ui-design/rules-task.md`).

## 먼저 읽을 것
`${CLAUDE_PLUGIN_ROOT}/references/practices/ui-spec.md`(화면 설계서와 와이어프레임을 쓰는 기준), `${CLAUDE_PLUGIN_ROOT}/references/practices/test-rules.md`, 기획 정본 `spec\brief.md`(「화면 흐름」의 이 묶음 화면 id·이동 표, 「정책」), `spec\overview.md` 「용어」, `spec\{묶음}.md`, UI 규약 `ui\rules.md`(있으면), `recon.md` 「UI 규약」, 기존 화면이 있으면 그 코드(`recon.md`가 가리키는 화면 폴더).

## 하는 일
1. **결정 지도를 먼저 쓴다.** 배치·조작 흐름이 둘 이상 성립하고 취향이나 운영 방식에 따라 갈리는 결정은 사용자 결정이다(시안으로 묻는다, 아래 4). 요구사항·용어·UI 규약·기존 화면의 관례(파일:줄)로 하나로 정해지면 관례 결정이다. 고객·운영자가 읽는 문구를 담당이 정했으면 알릴 결정이다.
2. 정본 `ui\{묶음}.md`를 쓴다(화면 id와 이동은 기획을 따르고 바꾸지 않는다. 바꿔야 하면 「정해 주실 것」): 화면마다 목적, 요소(위계 순서, 요소 id), 배치(위에서부터·좌우), 상태별로 보이는 것(비어 있음·읽는 중·오류·입력 검사 실패·권한 없음. 해당 없으면 "해당 없음"과 이유 한 줄), 조작마다 결과·피드백·되돌리기, 문구(개요 「용어」에 있는 대상은 그 이름 그대로), 닿는 FR·AC 번호. **기존 화면을 고치는 변경**이면 바뀌는 화면과 바뀌는 상태·요소만 적고 나머지는 "기존 그대로(파일:줄)"로 둔다.
3. 와이어프레임 `ui\wireframes\{묶음}.html`을 그린다(`ui-spec`의 규약: 화면마다 `data-screen`, 요소마다 `data-el`, 상태 블록은 `data-state`, 시안은 `data-variant`, 꾸밈 없는 선 그림, 외부 자원 없음, 파일 하나로 열림, 틀 폭은 `ui\rules.md`가 정한 값). 제품 코드가 아니다. 코드 폴더에 두지 않는다. 기존 화면 부분 변경이면 바뀌는 화면만 그린다.
4. **시안**: 사용자가 보고 골라야 하는 결정은 안을 둘 그려(`data-variant="가"`·`"나"`) 「정해 주실 것」 한 항목에 쓴다 — 무엇을 정하는지 / 안마다 달라지는 것 한 줄 / **안마다 글자 배치도**(요소를 위에서부터 한 줄씩, 좌우는 `|`로) / 보는 방법(`file:///` 경로와 `data-variant` 값) / 추천과 이유. 셋을 넘으면 둘로 줄인다. 시안끼리 얽혀 조합이 늘면 거기서 닫는다(`writer.md` 2절). 답의 반영은 메인이 정본 「시안」 표 아래에 `채택: 안 (가) — {답 시각}` 한 줄을 더하는 것뿐이다(와이어프레임은 그대로 둔다. 설계·구현은 채택 줄을 따른다).
5. 「알릴 것」 첫 줄에 늘 와이어프레임 경로를 둔다(`와이어프레임: file:///…/ui/wireframes/{묶음}.html`). 시안이 없어도 사용자가 볼 수 있게.
6. UI 규약(`ui\rules.md`)과 어긋나게 정한 곳은 이유와 함께 「알릴 것」. 규약이 없으면 적지 않는다.
7. 화면을 만들다 요구사항이 모자라거나 부딪치면(요소가 필요한데 FR이 없음, 두 FR이 한 화면에서 충돌) 추측으로 메우지 않고 「정해 주실 것」(요구사항을 바꾸는 제안)에 올린다.

## 승인 화면
- 정해 주실 것: 시안 선택지(위 4의 꼴), 요구사항을 바꾸는 제안, 답 없는 사용자 결정
- 하실 일·허용 요청: 보통 `- 없음`
- 알릴 것: 첫 줄 와이어프레임 경로, UI 규약과 어긋난 곳, 알릴 결정(고객·운영자가 읽는 문구·배치를 담당이 정한 것), "기존 그대로"로 둔 화면
- 답하신 것의 반영: 기획·상세의 답을 화면에 어떻게 옮겼는지
- 확인 안 된 것: 실기기·실제 데이터(긴 이름, 많은 건수, 작은 화면, 다른 글꼴)로 보지 않은 가정과 확인할 task
- 건수만: 화면 수, 상태 수, 용어 대조를 마친 문구 수, 관례 결정 수와 위치

## 자체 검증 (읽기 판정)
**판정의 경계**: 판정자는 파일만 본다(공통 계약 「판정 시점의 사실」). 이 task의 자체 검증은 *정합*(요구사항의 화면·조작이 다 있는가, 상태·조작·문구가 빠짐없는가, 와이어프레임이 설계서와 1:1인가)만 보고, *좋고 나쁨*(배치·취향)은 시안 선택지로 사용자에게 간다. 판정자는 「권장」에 배치·취향을 쓰지 않는다(쓰면 작성자가 그것을 고치려 재시도하는 고리가 생긴다).

원 산출물은 머리 파일 「건드릴 파일」의 `ui\{묶음}.md`와 `ui\wireframes\{묶음}.html`이고, 대조 원천은 `spec\brief.md` 「화면 흐름」, `spec\{묶음}.md`, `spec\overview.md` 「용어」, `ui\rules.md`다.
1. 기획 「화면 흐름」의 이 묶음 화면 id가 설계서에 모두 있고 다른 id가 없다. 그리고 `spec\{묶음}.md`에서 화면·표시·조작을 말하는 FR·AC마다 설계서의 어느 화면·요소에 연결됐다(판정자가 FR·AC를 하나씩 **전부** 대조. 기존 그대로인 화면은 "기존 그대로" 표시로 연결된 것으로 본다).
2. 화면마다 상태 다섯 줄이 있고, 각 줄에 보이는 것 또는 "해당 없음"과 이유가 있다(이유의 타당성은 판정하지 않는다. 칸이 비었으면 실패).
3. 조작마다 결과 칸이 비어 있지 않고, 기획 이동 표의 이 묶음 이동이 설계서 조작 표에 모두 있다.
4. 개요 「용어」에 있는 대상을 설계서가 다른 이름으로 부르지 않는다(판정자가 용어 목록의 이름마다 설계서를 검색. 용어에 없는 문구는 "담당이 채움" 표시 여부만 본다).
5. 집합 대조: 설계서 요소 표의 요소 id 집합 == 와이어프레임 `data-el` 값 집합(`grep -o 'data-el="[^"]*"' | sort -u`). 상태 블록(`data-state`) 안의 요소는 같은 id를 다시 쓴다. 시안 전용 요소(`data-variant` 블록에만 있는 요소)는 설계서 「시안」 표에 있어야 한다. 화면 id 집합도 같게(`data-screen`). 어느 한쪽에만 있으면 실패.
6. `ui\rules.md`가 있으면: 설계서가 규약의 토큰·모양·문구 톤을 따르거나 어긋난 곳이 「알릴 것」에 있다. 없으면(부분 변경만 있는 실행) 설계서의 바뀌는 요소마다 따르는 기존 스타일 위치(파일:줄)가 있다.
7. 시안이 둘 이상이면 「정해 주실 것」 항목에 안마다 글자 배치도와 보는 방법이 있고, 설계서 「시안」 표에 안마다 달라지는 요소가 있다.
8. 구성 요소·클래스·데이터 구조·저장 형식을 정한 문장이 없다.

# 마무리 task (`wrap-up`)

검증이 끝난 변경을 넘길 수 있는 상태로 정리하고, 개발 기준 브랜치에 넣는다. 앞 절반(문서와 내보낼 명령의 준비)은 `devflow-harness:release-writer`가, 뒤 절반(내보내기 실행)은 메인이 한다. 내보내기의 실행 승인은 늘 사람에게 간다. 1.2.0부터 시작한 마무리의 결과 승인은 `exec.py --verify` 실패, `불일치`, 얼린 줄대로 돌지 않음, 성질 `위험`일 때만 묻고 그 밖은 알림이다(그 전 task는 늘 묻는다). 단계는 머리 파일 `stage`(`실행승인` → `실행` → `결과승인` → `끝`)이고, 중간에 끊겼을 때는 `stage`·`external_progress`·`exec.md`로 가린다.

시작 조건은 `board.py --ready`가 본다(배포 밖의 모든 task가 끝남: 완료·보류·백로그·보류에 막힘, 이번 회차 수정 흐름 합쳐짐). 남기는 보류는 `screen.py`가 화면 「알릴 것」에 "[보류로 남김]"으로 붙인다. 코드 폴더는 통합 폴더(흐름이 하나면 그 흐름 폴더).

## 먼저 읽을 것
`${CLAUDE_PLUGIN_ROOT}/references/practices/release-practice.md`(문서 갱신과 남은 일 정리의 방법).

## 하는 일
앞 절반(준비, 작성자):
0. 「승인 화면」 `### 리뷰 자료`에 이 실행이 한 일을 쓰는 쪽의 말로 두세 문장 쓴다(1.2.0부터 시작한 마무리. 정본과 `run-map.md`가 재료다).
1. 문서 갱신: README, 운영 안내 등 이번 변경으로 틀려진 문서를 코드 폴더에서 고친다. 커밋하지 않는다(메인이 한다). 고친 문서마다 무엇을 왜 고쳤는지 본문에 적는다.
2. 인수 기준 추적표: 기준마다 소유한 검증의 판정을 모은다(검증 task들의 `result.md`의 추적표 절만 읽는다).
3. 배포 메모: 이 task 폴더의 `unverified-list.md`(각 task의 「확인 안 된 것」)를 빠짐없이 옮기고, 이번 변경에 든 마이그레이션·환경 변수·외부 설정 변경을 코드 폴더의 변경에서 찾아 적는다. 이 실행에 배포 계획 task가 있으면 그 사전 조건·배포 뒤 확인의 원천이 되고, 없으면 다음 배포 때 확인할 것으로 남긴다.
4. 백로그 목록: 이 task 폴더의 `backlog-list.md`를 한 줄씩.
5. 정리 목록: 지울 코드 폴더, 지울 브랜치, 실행 중 받은 임시 권한(→ 「하실 일·허용 요청」). 이 실행에 아직 끝나지 않은 배포 계획·실행 task가 있으면 그 배포 폴더(통합 폴더, 흐름이 하나면 흐름 폴더)와 브랜치는 "배포 task가 끝난 뒤"로 적고 지금 지울 목록에 넣지 않는다. 작성자는 지우지 않는다. 지우기는 메인이 실행을 닫을 때 한다.
5-1. **프로젝트에 넣기**(`docs_base_commit`이 있는 실행): `${CLAUDE_PLUGIN_ROOT}/references/practices/project-docs/insert.md`. 메인이 합쳐 둔 표 `docs-insert.md`를 읽고, 결정 기록과 위험·미확인 목록을 쓰고, 넣은 작성 문서마다 `- 지키는 경로:` 줄을 본문에 쓴다. 생성 명령이 없으면 돌리지 않고 `- 생성 명령 제안:` 줄을 본문에 쓴다. 넣을 문서를 손으로 고치지 않는다.
6. 비밀값 검색: 내보낼 브랜치의 변경에서 비밀값 패턴을 검색한 결과(명령과 건수).
   - 비밀값 검색에서 걸린 것이 있으면 값을 옮겨 적지 않고 파일:줄만 「정해 주실 것」에 올린다.
7. **내보낼 명령**: `recon.md`와 프로젝트 설정의 내보내기 방식대로, 자리 표시 없이 그대로 실행할 형태로 「정해 주실 것」의 `cmd` 울타리에 적는다(`formats.md` 4절. 원래 폴더에서 bash로 돈다: `git -C` 없이, 경로는 `/`로).
   - 병합 방식(개발 기준 브랜치가 원격에 없어 PR을 만들 수 없는 저장소): 원래 폴더에서 통합 브랜치(흐름이 하나면 흐름 브랜치)를 개발 기준 브랜치에 `git merge --ff-only`로 넣는 명령(넣은 끝이 최종 CI의 검증 commit이어야 한다. 앞감기가 안 되면 실행 전에 거부된다).
   - PR 방식: push와 PR 생성 명령, PR 설명.

## 승인 화면
화면 맨 앞은 리뷰 자료와 스크립트가 만드는 마무리 리뷰다. 차례는 「먼저 보실 것」(`지금 문제 있음`, 시험 끄기·삭제, 받아들인 위험, 미룬 실물 확인, 재지 못함), 실행 지도 전체(`[메인]` 기록, 뺀 검증 포함), 넣을 산출물, 남은 확인 안 된 것, 코드 확인, 흐름 리뷰 뒤에 바뀐 것, 시험 변화이고 내보낼 명령은 그 뒤다. 작성자는 이 줄들을 옮겨 쓰지 않는다.
- 정해 주실 것: 내보낼 명령(그대로). "이 명령을 원래 폴더에서 실행합니다"
- 하실 일·허용 요청: 정리 목록
- 알릴 것: 고친 문서, 다음 배포 때 확인할 것
- 확인 안 된 것: 판정불가로 남은 인수 기준
- 건수만: 통과한 인수 기준 수, 백로그 task 수

## 자체 검증 (실행 판정 + 읽기 판정)
앞 절반의 자체 검증이다. 읽기 판정 뒤 메인이 문서를 커밋하고, 실행 판정이 그 HEAD에서 최종 CI를 돌린 뒤 실행 승인으로 간다(`references/kinds/wrap-up/main-order.md`).
1. 갱신한 문서의 명령·경로·설명이 실제 코드와 맞다(읽기 판정이 문서의 명령과 경로를 코드 폴더에서 하나씩 확인).
2. 비밀값 검색 결과 0건(메인이 같은 검색을 다시 돌림, "메인 실행").
3. 이번 실행과 무관한 파일이 내보낼 브랜치의 변경에 없다(메인이 `git diff --stat {기준}..{브랜치}`의 파일을 task들의 「건드릴 파일」과 대조, "기록 대조").
4. 추적표의 모든 인수 기준에 판정이 있다. 배포 메모에 각 task의 미확인 항목이 빠짐없이 있다(읽기 판정이 `unverified-list.md`와 대조).
5. 문서 커밋한 HEAD의 최종 배포 후보 CI: 전체 검증, 검증 commit = 그 HEAD(실행 판정, `references/kinds/wrap-up/run-check.md`).
6. 리뷰 자료의 이 실행이 한 일이 `run-map.md`와 어긋나지 않는다(읽기 판정).
7. 넣기가 있는 실행: `docs-insert.md`의 표가 코드 폴더의 `docs/` 변경과 맞고, 풀리지 않은 `같은 절 두 곳`이 없으며, 넣은 작성 문서마다 지키는 경로가 있다(읽기 판정).
8. 생성 명령이 있으면 `project_docs.py … --generate {코드 폴더} --check` 통과(실행 판정).

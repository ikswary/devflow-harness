# 설계 task: 실행 전체 몫

읽는 때: 실행 전체 몫을 쓰는 설계 task일 때(누가 쓰는지는 `references/kinds/design.md` 「하는 일」).

정본에 쓰는 것:
- 흐름 지도: 어느 묶음이 어느 설계 task와 흐름으로 가는지(묶음과 흐름이 1:1이 아니어도 된다), 그리고 **흐름 사이 겹침마다 경우와 이유**(경우는 `references/kinds/design.md` 「하는 일」의 세 가지). 흐름은 서로 기다리지 않는 것이 목표다. 다른 흐름 코드가 끝나 합쳐지길 기다리면 그 흐름의 검증·수정·승인 대기가 전부 대기 시간이 된다.
- 공용 형식·오류 코드·상수 위치. 새로 만들어야 하면 그것을 만드는 흐름을 정하고, 쓰는 흐름은 그 흐름에 이어 붙인다.
- 전체 검증의 관점 목록과 관점별 범위(흐름이 둘 이상일 때), 마무리 task의 행.
- 사용자만 할 수 있는 계정·콘솔 작업 목록(「하실 일·허용 요청」으로).
- 배포 계획: 요청에 배포가 없으면 "이번 실행에서는 배포하지 않는다". 있으면 환경·시점마다 한 줄(환경, 어느 task 뒤, 올릴 것, 배포 뒤 확인(읽기/쓰기), 되돌릴 수 있는지, 비용, **배포 뒤 적을 문서**: 배포 결과로만 쓸 수 있는 문서 절과 적을 값(올라간 버전, 첫 적용 사실 등). 배포 도구가 읽는 문서는 고르지 않는다. 없으면 "없음"). 운영 줄이 있고 프로젝트 설정에 운영 브랜치가 있는데, 프로젝트의 운영 브랜치 규칙 절이 비어 있거나 병합을 적고 있으면 그 절 수정을 이번 실행의 문서 구현 행 범위에 넣는다(`references/kinds/deploy-plan.md` 「자식 행 계약」). 운영 줄은 dev 줄과 같은 커밋을 올리고, 배포 뒤 확인은 읽기만 둔다(쓰기 경로는 dev 쓰기 확인과 연결 경로 대조로 보증, `references/kinds/deploy-plan.md` 「자식 행 계약」). 배포 뒤 적을 문서는 배포 실행 task의 뒤 절반(배포 기록)이 쓰므로 그것을 위한 구현·마무리 행을 따로 만들지 않는다. 배포 방식이나 운영 배포 여부가 요청·이전 답으로 정해지지 않으면 「정해 주실 것」(사용자 결정)이다. 처음 들어가는 자원처럼 되돌릴 수 없는 배포는 알릴 결정이 아니라 사용자 결정으로 올린다. 환경 자체가 없어 만들어야 하면(배포 준비) 「정해 주실 것」으로 올리고 닫는다(배포 준비 task는 아직 하네스에 없다).

자식 목록에 더하는 행:
- 실행 전체 몫을 쓰는 설계 task는: 전체 검증의 관점마다 task 행(`kind: full-verify`, 흐름이 둘 이상일 때), 마무리 task 행(`kind: wrap-up`), 배포 계획 한 줄마다 배포 계획 task 행(`kind: deploy-plan`, 모두 마무리 task에만 의존. 환경 사이 순서(dev 뒤 운영)는 계획끼리 걸지 않고 배포 실행에서 건다(`references/kinds/deploy-plan.md` 「자식 행 계약」). 배포 실행 task 행은 배포 계획이 쓴다). 고르지 않은 운영 배포는 `[백로그]` 행. 배포 선택지가 아직 「정해 주실 것」이면 줄마다 `- option: 배포/{안}`(`formats.md` 4절. 고르지 않은 운영 배포를 백로그로 남기면 메인이 `--backlog-option`).
- 배포로만 닫히는 인수 기준은 설계가 배포 계획 행의 닫는 인수 기준에 넣어야 배포 실행 행으로 이어진다. [RP-08]

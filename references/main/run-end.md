## 9. 실행의 끝

내보내기를 맡은 task가 `완료`되고(내보내기까지 끝났거나, 사용자가 내보내기를 직접 하기로 했으면(직접 넣은 병합은 `exec.py --verify`가 받는 브랜치에 들어 있는지로 받는다). 배포만으로 시작해 그 task가 없으면 이 조건은 없다) 배포를 계획·실행하는 task가 모두 끝났으면(끝 = `devflow_lib.settled`: `완료`·`보류`·`백로그`·보류에 막힌 `대기`. 배포 명령을 실행하는 task의 완료는 `stage: 끝`). 시작할 수 있는 task·도는 task·승인 대기가 없는데 남은 task가 모두 보류에 막혔으면(`--ready`의 `! 끝 질문`) 보류 목록을 보여 주고 끝낼지 묻는다:
1. 지표를 손으로 세어 `_workspace\measure.md`에 한 행을 더한다(열은 그 파일의 머리). 집계 스크립트는 아직 없다.
2. 최종 보고: task별 결과 한 줄(`board.py` 표), 백로그 목록, 받아들인 위험, 「이번 실행의 값」 가운데 바꿀 근거가 생긴 것, 그리고 **사용성 확인**(아래).
3. **코드 폴더 정리**(최종 보고와 같은 화면에서 한 번 승인). 대상은 이 실행의 코드 폴더 전부(`flow.md`의 `dir`과 `run.md`의 `integration_dir`. 통합 폴더는 `flow.md`가 없을 수 있다)와, `git worktree list`에서 `harness/` 브랜치를 꺼낸 폴더 가운데 `run.md`가 `완료`인 다른 실행의 것. 완료가 아닌 채 끝난(위의 끝) 배포 쪽 task가 있어도 넣는다(다시 열면 배포 폴더를 새로 만든다, `formats.md` 1절 `deploy-{n}`). 메인이 폴더마다 확인한다.
   - `git status --porcelain`이 비어 있다. 아니면 목록에서 빼고 이유를 적는다.
   - 브랜치가 개발 기준 브랜치에 들어 있다(`git merge-base --is-ancestor {브랜치} {개발 기준 브랜치}`). 아니면 목록에서 뺀다.
   - git이 무시하는 파일(`git status --porcelain --ignored`) 가운데 실행 기록(`exec.md`, `logs\`, `result.md`)이 경로로 가리키는 파일은 그 task의 `logs\`로 복사하고 같은지 확인한다(`cmp`). 다시 만들 수 있는 빌드 산출물과 비밀 파일 사본은 복사하지 않는다.
   - 승인 화면에 지울 폴더·브랜치와 명령을 그대로 보인다: 폴더마다 `git -C {원래 폴더} worktree remove {폴더}` 다음 `git -C {원래 폴더} branch -d {브랜치}`. `--force`와 `-D`는 쓰지 않는다. 실패하면 그 폴더는 남기고 출력을 보인다.
   - 승인되면 실행하고, 지운 폴더의 `flow.md`를 `status: 폴더 지움`으로 바꾸고(`branch`·`dir`는 기록으로 남긴다. 다시 연 회차가 그 이름을 쓰지 못하게 한다) `journal.md`에 폴더마다 한 줄. 권한 시스템이 거부하면 7절대로 명령을 「하실 일」로 넘긴다. 사용자가 미루면 `run.md` 「남은 정리」에 목록을 적는다(다음 실행의 이 단계가 다른 실행의 남은 폴더로 다시 잡는다).
4. `run.md`를 `status: 완료`로 바꾸고 `journal.md`에 한 줄.

첫 실행들의 최종 보고에서 사용자에게 확인받을 것: 병합 단계와 끝맺음 단계를 task 하나씩으로 둔 것과 검증·다시 하는 검증을 둘로 나눈 것이 보드와 재개에서 쓰기 편했는지 / 승인 화면의 칸 구성(특히 요구사항·원인을 찾는 task·끝맺음) / 승인 하나의 크기가 어땠는지(화면 첫 줄의 수와 `나눠서 다시`를 고른 횟수) / 알림으로 지나간 task에서 숨은 예외가 몇 건 나왔는지.

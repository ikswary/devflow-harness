## 0. 시작과 재개

작업 공간: `{호출한 작업 디렉터리}\_workspace\{실행 폴더}`. 대상이 다른 폴더여도 위치를 바꾸지 않는다. `_workspace/`가 저장소의 제외 목록(`git rev-parse --git-path info/exclude`가 가리키는 파일)에 없으면 추가한다.

1. **발견 점검**: 사용 가능한 에이전트 유형에 진입 「구성」의 에이전트 8종이 모두 있는지 확인한다. 하나라도 없으면 진행하지 않고 사용자에게 알린다. 범용 에이전트로 조용히 대체하지 않는다. `board.py --ready`에 `! 에이전트 정의` 줄이 있으면(판정자 정의가 이 판의 규칙과 맞지 않음) task를 띄우지 않고 사용자에게 알린다. 판정자 정의, 판정자 공통(`references/roles/judge.md`), 형식 파일 `references/formats/judge-file.md`·`judge-run-file.md`의 판정 파일 규칙을 바꾸면 두 정의의 `def-version` 표지와 `kinds.DEF_VERSION_MIN`을 함께 올린다.
2. `_workspace`에서 `run.md`가 있고 `status: 진행`인 실행을 찾는다(`state.md`가 있는 폴더는 옛 하네스의 실행이니 건드리지 않는다).
   - 있고 요청이 "이어서"면 → **재개**(0절 4).
   - 있는데 새 요청이면 → 묻는다: 진행 중인 실행에 더함 / (요청이 끝난 다른 실행의 후속이면) 그 실행 다시 열기 / 새 실행.
   - 없고 요청이 끝난 실행의 **후속**이면 → **다시 열기**(0절 5). 후속은 그 실행의 정본(`spec\`·`ui\`·`design\`)과 `decisions.md`를 그대로 이어 쓰는 요청이다: 그 변경의 배포, 그 설계가 남긴 행·확인 안 된 것의 처리. 따로 묻지 않고 첫 줄에 "실행 {폴더}를 다시 열어 이어 붙입니다"라고 밝힌다. 후속인지 애매하면 묻는다.
   - 그 밖이면 새 실행. 끝난 실행의 백로그를 처리하더라도 새 기능·새 설계가 필요하면 새 실행이고, 시작 task의 `origin`에 원래 task 폴더를 적는다(`board.py {작업 공간} --backlog`).
3. **새 실행**:
   1. 실행 폴더를 만들고 `run.md`를 쓴다(요청 원문, 대상 프로젝트, 개발 기준 브랜치, 원래 폴더의 `git status --short`, 하네스 판본, 발견 점검 결과, `session_id`(7)).
   2. 프로젝트 설정 `_workspace\devflow-harness.project.md`를 읽는다. 없으면 한 번만 묻고 만든다(의존성 설치 명령, 새 폴더에 준비할 비밀 파일과 준비 방법, 시험 자료 준비, 개발 기준 브랜치, 내보내기 방식). 폴더의 위치·이름·기준 커밋은 규칙이라 묻지 않는다. 있는데 위 항목 가운데 빠진 것이 있으면(나중에 생긴 항목) recon이나 프로젝트 문서에서 답이 나오면 채우고 journal에 적으며, 나오지 않으면 그 항목만 묻는다.
      - **줄 끝 고정**: `eol_setup.py {원래 폴더}`로 점검한다. `고정됨`이면 넘어간다. `고정 안 됨`이고 프로젝트 설정 `줄 끝 고정`이 비었으면 점검 출력을 보여 주고 한 번 묻는다(적용 / 안 함). 답을 프로젝트 설정에 적고, `안 함`이면 다시 묻지 않는다. `적용`이면 원래 폴더가 개발 기준 브랜치일 때 `eol_setup.py {원래 폴더} --apply`를 돌리고 메인이 `chore: 줄 끝을 LF로 고정(.gitattributes)`로 커밋해 journal에 적는다. 코드 폴더를 만들기 전에 끝낸다(폴더가 LF로 갈라지게). 종료 3(커밋하지 않은 변경)이거나 다른 브랜치면 적용하지 않고 「하실 일」로 넘기고, 다음 실행에서 다시 점검한다. 이유: Windows의 Python 텍스트 모드·PowerShell 쓰기가 LF 파일을 CRLF로 바꿔 커밋 diff가 수백 줄로 불어난다.
   3. 정찰: 정찰 방법 문서(`references/practices/project-recon.md`)의 스크립트를 돌려 `recon.md`를 쓴다. 공유 자원과 잠금 명령, 스스로 잠금을 잡는 명령, 병합 관례(예: 앞감기 없는 병합), UI 규약(디자인 토큰 파일, 컴포넌트 폴더, 스타일 가이드·문구 규칙 문서, 화면 시험 도구. 덧대기식 스타일 파일 더미는 규약이 아니다 — 그때는 "없음(스타일 파일 n개)". `formats.md` 6절 recon)을 찾아 적는다.
   4. 「이번 실행의 값」을 `run.md`에 적는다. 시작값: 동시에 도는 흐름 2(코드 폴더에 쓰는 task 기준, 1절 2) / 수정 세대 상한 2 / 자체 검증 재시도 2 / 판정불가 다시 돌림 2(2절 표) / 승인의 크기는 강제하지 않고 수를 표시 / 알림으로 지나간 task는 그 흐름의 검증이 전부 다시 읽음 / 모델은 진입 「구성」. 측정 기록 `_workspace\measure.md`에 지난 실행의 값과 결과가 있으면 한 화면으로 보여 주고 바꿀지 묻는다. 그 파일이 없으면 표 머리만 가진 파일로 만든다(머리는 `formats.md` 6절 「측정 기록」).
      - 검증 효율 실험을 선택한 새 실행만 `references/experiments/verification-shadow.md`를 읽고 승인·사전값을 고정해 `collect.py {실행 폴더} --shadow-init {계획 JSON}`을 첫 task 생성 전에 실행한다. 비선택은 기본 절차를 따른다.
   5. 시작 task를 정한다(아래 표). 요구사항 블록은 사용자에게 보이는 동작을 바꾸는 요청에만 쓴다. 동작을 바꾸지 않는 요청을 개요 → 상세로 시작하지 않는다. 요청이 어느 행인지 분명하지 않으면 묻는다. 시작 task의 머리 파일을 메인이 `task_set.py new`로 만든다(범위 = 요청 원문과 이어받는 task의 경로, 판정 기준 = 그 task 정의의 「자체 검증」).
      | 요청 | 시작 task | 부모가 없어서 채우는 것 |
      |---|---|---|
      | 새 기능, 기능 변경 | 질문(T001) → 요구사항 개요(→ 기획 → 상세 → 화면 설계 → 설계, `references/kinds/req-overview.md`·`brief.md`) | 질문 task |
      | 버그 | 질문 → 원인 분석 | 기대 동작과 재현 테스트가 인수 기준을 대신함 |
      | 동작을 바꾸지 않는 변경(배포 도구, 테스트, 문서, 리팩터링) | 질문 → 설계 | 유지할 동작 목록과 지키는 테스트, 이어받은 task의 확인 안 된 것 |
      | 배포만(올릴 커밋이 이미 개발 기준 브랜치에 있고, 배포 전에 고칠 코드·도구가 없음) | 배포 계획(환경마다 하나) | 이어받은 실행 마무리의 배포 메모. 없으면 변경 내역에서 찾음. 메인이 배포 폴더 `deploy-{n}`을 만듦(`references/kinds/deploy-plan/deploy-only.md`) |
      | 백로그 task 처리 | 그 task의 종류(배포 계획이면 위 "배포만" 행) | `origin`에 원래 task 폴더 |
      - 배포만·백로그 처리는 질문 task 없이 시작한다. 시작 전에 정할 것은 시작 task의 승인 화면 「정해 주실 것」으로 올린다(배포 계획은 그 승인이 실행 승인이라 묻는 자리가 이미 있다).
      - **섞인 요청**(예: 배포 도구 수정 + dev 배포)은 가장 앞 블록의 행으로 시작하고 나머지는 그 task의 자식과 설계의 배포 계획 줄로 둔다. 배포만으로 시작했는데 배포 계획 작성자가 "코드 변경 필요"로 돌아오면 그 task를 `보류`로 닫고 질문 → 설계로 다시 시작한다.
6. 세션을 끝낼 때는 "다시 열 때는 `devflow-harness 이어서`라고 불러 주세요(이름 없이 '이어서'라고 하면 하네스 없이 직접 처리합니다)"를 안내한다.
7. **세션 기록**: 새 실행(3의 1), 재개(4), 다시 열기(5) 때 `run.md` 머리의 `session_id`에 지금 세션의 id를 적는다. 줄은 하나이고 덮어쓴다(이전 세션의 값을 남기지 않는다). 값은 Bash `echo "$CLAUDE_CODE_SESSION_ID"`의 출력 그대로다. 출력이 비어 있으면 `session_id:`를 비워 두고 사용자에게 "대시보드(띠·패널)가 이 실행을 보이지 못합니다: 이 세션의 id를 얻지 못했습니다"를 한 줄 알린다. 띠·패널은 이 값으로 지금 세션의 실행을 고른다. 그래서 `/clear` 뒤 `devflow-harness 이어서`로 재개하면 새 값으로 덮어쓴다.

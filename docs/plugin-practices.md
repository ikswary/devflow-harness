# 플러그인·스킬을 만들고 유지하는 원칙

devflow-harness를 고칠 때 따르는 원칙과 그 근거다. 근거는 두 조사다(`_workspace/`는 git에서 빠진 로컬 작업 기록이다. 공개 저장소에서는 이 문서의 인용이 근거다).
- 공식 문서: `_workspace/research-official-docs.md`(Claude Code skills·plugins·sub-agents·plugin-evals·memory 문서, Anthropic 스킬 작성 가이드)
- 설치된 본보기: `_workspace/research-local-exemplars.md`(harness 플러그인의 harness·evolve 스킬, skill-creator, 사용자 스킬)

고치는 차례는 `references/main/maintain.md`가 짧게 가리키고, 기계로 지킬 수 있는 것은 시험(`tests/py/test_plugin_practices.py` 등)이 건다. 이 문서는 그 이유와 판단 기준이다. 원칙을 바꾸면 이 문서, maintain.md, 시험을 한 묶음으로 고치고 CHANGELOG에 이유를 적는다.

## 1. 고치는 법 (피드백을 하네스에 넣을 때)

1. **원인으로 일반화한다.** 사례 하나에 규칙 하나를 더하지 않는다. "왜 이 결과가 나왔나"에서 빠진 기준을 찾고 그 기준을 고친다(evolve "일반화 없는 반영 금지").
2. **결함과 규칙을 가른다.** 스크립트가 문서대로 돌지 않는 결함은 바로 고치고 시험을 붙인다. 새 규칙(사람·에이전트가 지킬 문장)은 같은 신호가 두 번 나올 때까지 미뤄 두고, 한 번 본 신호는 다음 판 후보로 CHANGELOG 행에 적는다. 규칙이 늘수록 따르는 정도가 떨어지고 서로 부딪힌다(memory.md "The more specific and concise your instructions, the more consistently Claude follows them.").
3. **한 번에 하나.** 커밋은 변경 하나마다, 그 변경이 닿는 시험을 바로 돌린다. 비싼 비교(목적 시험)는 판 단위로 묶는다.
4. **앞 결정과 대조한다.** 고치기 전에 CHANGELOG와 결정 기록에서 같은 자리를 반대로 고친 적이 있는지 본다. 되돌리는 방향이면 둘 다 만족하는 기준을 찾고, 그래도 부딪히면 사용자에게 묻는다.
5. **규칙마다 이유를 쓴다.** 이유를 알면 에이전트가 경계 사례에서도 맞게 판단한다. 대문자 강조나 예외 없는 금지는 이유가 빠졌다는 신호다.
6. **반드시 지킬 규칙은 문장이 아니라 장치로.** 스크립트 관문, 시험, 훅으로 건다(skills.md "Claude skipped a rule that must hold every time: move the rule into a hook.").

## 2. 한 규칙은 한 곳에서 (문서와 검사)

- 같은 규칙을 문서와 스크립트 둘 다에 두면, 둘을 묶는 시험을 둔다. 1.3.0 목적 시험의 결함 대부분이 이 꼴이었다: 판정자는 문서대로 썼는데 검사가 문서에 없는 꼴을 요구했다(까닭 머리 `주장-출처`, 「정한 것」 칸 옮김, 빈 끝 칸).
- 검사가 요구하는 꼴(머리말, 칸 이름, 상수)은 문서에 그 글자대로 적고, 시험이 문서에 그 글자가 있는지 본다.
- 문서 상한 때문에 규칙을 다른 문서로 밀어낼 때는, 그 규칙을 지켜야 하는 에이전트의 「읽을 것」에 그 문서가 있는지 확인한다(1.3.0 진단 2: 판정자가 「전제」 규칙을 읽지 않음).

## 3. 구조 (스킬·에이전트·참조)

- **SKILL.md는 목차다.** 500줄 미만(공식), 이 저장소는 6,144바이트(시험). 단계 파일 표로 그때 읽을 문서를 가리키고, 참조는 한 단계로만 건다(best-practices "Keep references one level deep").
- **description은 무엇과 언제를 앞에.** 목록에서 1,536자(description+when_to_use)에서 잘리고 스펙 상한은 1,024자다. devflow는 이름으로 부를 때만 쓰므로 "부르면 안 되는 요청"이 중요하다(본보기는 대체로 pushy하게 쓰라고 하지만 이 하네스는 사용자 결정으로 좁혔다).
- **중요한 지시는 위에.** 스킬 본문은 로드 뒤 매 턴 비용이고, 압축 뒤에는 스킬마다 앞 5,000토큰만 되살아난다.
- **에이전트 정의는 계약이다.** description은 짧게(합계 15,000토큰 경고), 세부는 본문에. `tools`는 허용 목록. 플러그인 에이전트는 `hooks`·`mcpServers`·`permissionMode`를 무시하므로 쓰지 않는다. 서브에이전트는 대화를 보지 못하므로 입력은 프롬프트 틀(`formats/prompt.md`)에 다 둔다.
- **결정적인 일은 스크립트로.** 셈, 꼴 검사, 상태 전이는 스크립트가 하고, 에이전트는 판단만 한다. 스크립트를 "실행"하는지 "읽는지"를 문서에 밝힌다.
- **경로.** 플러그인 안 경로는 `${CLAUDE_PLUGIN_ROOT}` 아래, 슬래시. 설치본은 캐시 복사본이라 루트 밖 파일은 따라오지 않는다. `${CLAUDE_PLUGIN_ROOT}`에 상태를 쓰지 않는다(판마다 바뀜).

## 4. 평가 (구조 회귀와 행동 회귀)

| 갈래 | 무엇을 | 이 저장소의 장치 | 언제 |
|---|---|---|---|
| 구조 회귀 | 문서 크기, 읽는 양, 등록표 정합, 층 구조, 판본 | `tests/py`의 정합 시험 | 바꿀 때마다 |
| 스크립트 동작 | 상태 전이, 화면, 판정 읽기 | `tests/py` 단위 시험 | 바꿀 때마다(닿는 것: `python tests/py/select_tests.py --run`), 커밋 전(전체: `python -m pytest -q -p no:cacheprovider -n auto`) |
| 플러그인 꼴 | manifest, 경로, 훅 | `claude plugin validate --strict .` | 판을 낼 때 |
| 항상 켜진 비용 | 이름·설명 토큰 | `claude plugin details devflow-harness` | 판을 낼 때(값을 CHANGELOG에) |
| 행동 회귀 | 사람이 판단 재료를 받는가 | 목적 시험(작성자→판정→화면→결과를 모르는 승인자, 정답지 대조) | 판을 낼 때, 모델이 바뀔 때 |
| 트리거 | 이름으로 부를 때만 불리는가 | (없음. `claude plugin eval`의 `tool_used: Skill` 후보) | 설명을 고칠 때 |

- **기준선과 나란히.** 행동 비교는 고치기 전 판과 고친 판을 같은 고정 과제로 돌리고, 어느 판인지 모르는 판정자가 본다.
- **시험이 차이를 가려내는지부터.** 고치기 전 판도 통과하는 기준은 아무것도 재지 않는다. 새 시험은 고치기 전 코드에서 실패하는지 확인한다.
- **지시문에 사후 지식을 넣지 않는다.** 결과를 모르는 승인자에게 정답지 자리를 가리키는 문장을 주면 시험이 무효다.
- **모델을 고정해 잰다.** 모델 교체가 하네스 회귀로 보이지 않게. 에이전트 정의의 `model`이 고정이므로 새 모델이 나오면 목적 시험을 다시 돈다.

## 5. 판을 낼 때

1. `claude plugin validate --strict .`(경고도 실패로 본다)
2. `claude plugin details devflow-harness`의 Always-on 토큰을 CHANGELOG 판 행에 적는다(1.3.0 작업 때 설치본 1.2.1 기준 약 2,160).
3. 읽는 양 기준선을 다시 잡는다(maintain.md).
4. plugin·marketplace 판본, 판정자 def-version, README를 한 묶음으로.
5. 목적 시험(판단 지점이 걸린 task)으로 행동 회귀를 본다.
6. 이름(`name`)은 바꾸지 않는다. 판을 올리지 않고 push하면 사용자는 옛 판에 남는다.
